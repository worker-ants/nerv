# 화면 설계 (와이어프레임)

> **요약** — NERV(가칭)의 웹 화면 8종(S1 홈 대시보드 · S2 프로젝트 개요 · S3 스펙 상세 · S4 작업 보드 · S5 세션 모니터 · S6 리뷰 센터 · S7 받은 요청 · S8 설정·멤버)을 정보 구조·와이어프레임·상태 표현 규칙·인터랙션 규약 수준까지 확정한다. 설계의 축은 하나다 — **화면은 요구사항(FR)의 렌더링이며, 번호가 붙지 않는 요소는 그리지 않는다.** 세션 카드에는 업계 관례(상태·diff 통계·브랜치·activity feed·attach)에 더해 NERV의 차별 요소인 **hostname·에이전트 종류·하트비트·클레임한 Task·리스 잔여**를 필수로 표기해, clemvion에서 "다른 머신·세션이면 로컬에 안 보여" 사라졌던 정보를 화면 위로 끌어올린다. 기획자·디자이너가 터미널 없이 스펙을 쓰고 승인하며(P7), QA가 원시 diff 대신 정리된 finding을 보고 위험을 판단하며, 개발자가 죽은 세션을 사람 눈으로 감시하지 않는 것 — 이 세 가지가 화면이 증명해야 할 명제다. 이 문서의 HTML 파생본은 모든 화면을 실제 UI로 렌더링한 쇼케이스다.

## 1. 정보 구조(IA)와 내비게이션

### 1.1 화면 설계 5원칙

이 문서의 모든 화면 결정은 아래 다섯 원칙에서 파생된다. 원칙 1·2는 [문제 정의와 요구사항](../01-problem/pain-points.md)의 P4·P7에서, 3·4는 [협업 플랫폼의 에이전트 통합](../02-research/collab-platforms.md)이 정리한 업계 수렴 패턴에서, 5는 [clemvion 하네스 분석](../01-problem/clemvion-analysis.md)이 검증한 운영 경험에서 나왔다.

1. **화면은 요구사항의 렌더링이다.** 모든 화면 요소에는 FR/D 번호가 붙는다. 번호가 없는 요소는 그리지 않고, 반대로 FR에 있는 상태는 어느 화면에든 반드시 드러난다. 이 문서의 legend가 그 대응표다.
2. **묻지 않아도 보인다.** P4(구현 상태·다음 할 일 추적 곤란)의 본질은 정보 부재가 아니라 **합성 비용**이었다. clemvion에서 "다음에 뭘 하지"의 답은 로드맵 표 + spec status + in-progress 풀 + 감사 스크립트 2종을 사람이 눈으로 합쳐야 나왔다. NERV의 화면은 그 합성을 서버가 끝낸 뒤의 결과만 보여준다.
3. **에이전트는 항상 자신을 밝힌다.** 사람과 에이전트가 같은 리스트에 섞여도 액터 타입은 배지로 구분된다(D-08). "에이전트는 자신이 에이전트임을 항상 밝혀야 한다"는 Linear의 원칙과 GitHub 감사 로그의 `actor_is_agent` 플래그를 UI 계약으로 옮긴 것이다.
4. **행동은 카드 위에서 끝난다.** 승인·거절·코멘트, attach·stop, finding 해소는 목록을 떠나지 않고 카드 안에서 처리된다. 다만 되돌릴 수 없는 행동(거절, stop, 게이트 면제)은 사유 입력을 한 단계 요구한다.
5. **모르면 모른다고 말한다.** 게이트 판정 불가, 플랫폼 연결 끊김, 하트비트 유실은 조용히 통과시키되 **배너로 드러낸다**(D-14 fail-open + 관측 + 격상, NFR-05 로컬 폴백). 조용한 실패는 화면 설계 차원의 금지 사항이다.

> **D-08 — 행위자 모델: 사람 assignee + 에이전트 delegate 분리.** 화면에서 이 결정은 세 가지로 나타난다. ① Task 카드에 사람 아바타(assignee)와 AI 배지(delegate)가 **동시에** 찍힌다. ② 활동 피드·감사 로그의 모든 항목에 `is_agent` 구분이 보인다. ③ 에이전트가 단독으로 소유한 항목은 존재하지 않는다 — 책임자는 언제나 사람이다.

### 1.3 내비게이션 맵

화면 간 이동은 대부분 "숫자를 클릭하면 그 숫자를 만든 레코드로 간다"는 한 가지 규칙을 따른다. 커버리지 게이지의 28은 Requirement 목록으로, finding 큐의 3은 finding 상세로, 세션 카드의 diff는 PR로 간다.

```text
                              ┌──────────────────────────┐
     로그인 ───────────────▶  │  S1 홈 대시보드           │
                              └──┬────────┬─────────┬────┘
                 승인 대기 배지  │        │         │  프로젝트 카드
                    ┌───────────┘        │         └────────────┐
                    ▼                    ▼                      ▼
        ┌────────────────────┐   ┌───────────────┐   ┌────────────────────┐
        │  S7 받은 요청          │   │  알림 센터     │   │  S2 프로젝트 개요   │
        └──┬───────────┬─────┘   └───────────────┘   └──┬──────┬───────┬──┘
   스펙/CR │           │ 질문 응답                       │      │       │
           ▼           ▼                    스펙 트리 ◀──┘      │       └──▶ 커버리지
```

- **S7 → 요청 세션 딥링크**: 질문에 답하면 카드가 "요청 세션 `mac-02/claude-code`에 전달됨"으로 바뀌고, 그 텍스트가 S5 세션 상세로 가는 링크가 된다.
- **S6 → S3 역추적**: 모든 finding은 유래한 SpecVersion·Requirement를 갖는다(FR-09·FR-13). 이것이 P5(리뷰 출처 추적 곤란)의 화면 상 해답이다.
- **S5 → git forge**: diff 통계와 브랜치명은 PR로 나가는 외부 링크다. NERV는 코드 호스팅을 대체하지 않는다.

### 1.4 URL 규약

| 규칙 | 형태 | 이유 |
| --- | --- | --- |
| 리소스는 항상 **고정 ID**로 지목 | `/p/clemvion/specs/SPC-CWC-007` | 경로·제목이 바뀌어도 링크가 깨지지 않는다(FR-01, D-09). clemvion의 인덱스 문서 부패는 경로 참조가 원인이었다 |
| 프로젝트 소속은 URL 두 번째 세그먼트 | `/p/{project}/...` | 권한 검사 지점이 라우팅과 일치한다(FR-14) |
| 뷰 상태는 쿼리로 | `?diff=v3..v4`, `?severity=critical` | 공유 가능한 링크. 승인 요청 알림에 그대로 붙는다 |
| 세션·작업은 전역 유일 ID | `/p/clemvion/sessions/S-8f31` | 훅·MCP 응답이 반환하는 딥링크와 동일 형태(FR-07·FR-15) |

> 표기용 예시 ID(`SPC-`/`REQ-`/`TSK-`/`S-`/`FND-`/`CR-` 접두)는 이 문서의 화면 예시를 읽기 쉽게 하기 위한 것이다. 실제 ID 발급 규칙(서버 발급 해시 기반, D-04)과 접두 확정은 [데이터 모델](data-model.md)이 정의한다.

### 1.5 역할별 첫 화면

| 역할 | 로그인 후 착지 | 주로 쓰는 화면 | 화면에서 막히는 것 |
| --- | --- | --- | --- |
| `planner` | S1 → 받은 요청 | S3 · S7 · S2 | Requirement를 `verified`로 올리는 전이는 노출되지 않음 |
| `designer` | S1 → 받은 요청 | S3(design 타입) · S7 | 스펙 승인 권한은 지정 리뷰어일 때만 활성 |
| `developer` | S1 → 작업 보드 | S4 · S5 · S3 | 게이트 면제 버튼은 확인 다이얼로그 + 사유 필수 |
| `qa` | S1 → 리뷰 센터 | S6 · S2 커버리지 · S4 | `implemented → verified` 전이는 qa(및 admin)만 가능 |

| `admin` | S1 | S8 + 전 화면 | — |

권한은 버튼을 **숨기지 않고 비활성화**한다. 숨기면 "이 작업을 누가 할 수 있는가"를 사람이 다시 물어야 하고, 그 질문의 답이 없던 것이 clemvion의 `owner` 자유 텍스트 문제였다(P7·FR-14).

## 2. 화면별 와이어프레임

### 2.0 읽는 법

- 각 화면 아래의 `(n)` 마커는 legend의 번호와 대응하고, legend 항목 끝에 관련 **FR/D 번호**를 붙였다.
- 아스키 아트는 레이아웃과 정보 우선순위를 정의할 뿐 최종 비주얼이 아니다. 고충실도 렌더링은 [HTML 파생본](../html/ui-wireframes.html)에 있다.
- 예시 데이터는 [비전과 핵심 시나리오](vision.md)의 페르소나(지민·서연·도현·하나·유나)와 동일한 인물·호스트·수치를 쓴다.

8. **연결 Requirement 표** — 고정 ID + EARS 문장 + **구현 축 상태**. 문서 상태(approved)와 구현 상태(unimplemented)가 한 화면에서 서로 다른 값을 가질 수 있다는 것이 D-02의 요점이다. `FR-03 · D-02`

11. **초안 편집 리스 배지** — draft 버전이 편집 중이면 상단에 보유자를 **(사용자 · 표면 · 최신 갱신)**으로 표시한다. 웹 에디터 열기 / `nerv_spec_draft_upsert` 성공 시 자동 획득·갱신되고(TTL 30분 — Task 클레임 리스와 같은 상수), 리스를 쥔 `(user, session)` 이 아니면 읽기 전용 + **[이어받기]** 버튼이고(누르면 저장에 `takeover: true` 가 실린다 — 2026-08-30 개정), 뺏은 사실은 이벤트에 남는다. 리스는 1차 사전 조정이고 `base_hash` 비교-교환은 최후 방어선 — 역할이 달라 둘 다 유지한다. `FR-02 · D-04`
12. **터미널에서 이어쓰기** — 복사용 명령 `claude "/nerv:spec edit SPC-CWC-007"`을 제공한다. 터미널에서 열면 `takeover` 로 편집 리스를 이어받고, 반대 방향은 `nerv_spec_draft_upsert` 응답의 `web_url` 딥링크가 담당한다. 웹과 에이전트는 "두 개의 편집기"가 아니라 **하나의 draft에 대한 두 개의 입력 장치**이며, 스펙을 쓰는 에이전트 세션도 S5 세션 보드에 뜬다. `FR-07 · FR-15 · D-04`

2. **신원 3요소: 사용자 · hostname · 에이전트 종류** — NERV 세션 카드의 필수 표기. clemvion의 조율 상태는 전량 gitignored 로컬 파일이라 hostname 개념 자체가 없었고, 그래서 스펙 동시수정 검출이 "다른 머신·세션이면 로컬에 안 보여"라는 이유로 제거됐다. `FR-07 · D-04`
3. **클레임한 Task와 유래 스펙** — 세션이 무엇을 근거로 일하는지. 스펙 없는 세션은 보드에 뜨지 않는다. `FR-06 · FR-05`
4. **하트비트 · 리스 잔여 · 경과** — 세 시간 값의 의미가 다르다. 하트비트는 생존, 리스는 점유 만료, 경과는 비용. `D-13 · FR-06`
5. **브랜치 · diff 통계 · 변경 파일 수** — `+218 −34` 표기는 Claude Code on the web 세션 목록의 관례를 그대로 따른다. 클릭 시 PR로 이동. `FR-08`
6. **선언된 scope** — `spec_ids` + `file_globs`. 겹침 경고가 이 값으로 계산된다. 화면에 보여야 사람이 "왜 내가 차단됐는지" 안다. `FR-06 · D-04`
7. **액션 4종** — 로그 보기 · attach(딥링크) · steer(중단 없이 지시 추가) · stop. steer와 stop을 1급 동작으로 노출하는 것은 GitHub mission control의 검증된 패턴이다. `FR-08`
8. **awaiting_input의 목적지 표기** — 누가 답해야 하는지를 세션 카드가 직접 말한다. 질문이 "남의 터미널에 떴다 사라지는" 상태의 반대말. `FR-11 · D-13`
9. **stale과 자동 회수** — 무활동 30분 임계 초과 시 자동 전이 + 클레임 회수. 회수된 Task 번호를 카드에 남긴다. `D-13 · FR-06`
10. **fail-open 배너** — 게이트 판정 불가가 연속될 때 진행은 허용하되 카운터를 노출하고, 임계 초과 시 "게이트가 사실상 꺼짐"으로 격상한다. `D-14 · FR-10`
11. **Activity 타임라인** — `thought / action / elicitation / response / error` 5종 타입드 로그. 편집 가능한 코멘트가 아니라 **불변 레코드**다. `FR-08 · D-10`
12. **산출물 역링크** — 커밋·PR·리뷰·질문으로 나가는 링크. "이 코드가 어느 세션에서 나왔나"(P5)의 답이 여기서 닫힌다. `FR-09 · FR-16`

> **근거 · clemvion 실측** — `clemvion:.claude/state/`의 조율 상태는 전부 gitignored 로컬 파일이고 hostname 필드가 없다. 하네스는 약 7,600줄의 훅 코드(최대 단일 훅 1,005줄)로 단일 호스트 안에서 이 화면의 일부를 흉내 냈지만, 두 번째 머신이 등장하는 순간 성립하지 않았다. 서버가 모든 세션의 선언을 보면 이 표는 SQL 한 번이다.

8. **BYPASS 기록** — 면제한 사람·시각·사유가 남는다. **면제가 조용히 일어나지 않는 것 자체가 기능이다.** `FR-10 · FR-16 · D-06`

> **근거 · clemvion 실측** — 이 화면이 대체하는 것은 파일 13,777개(131MB)의 `clemvion:review/`다. 73일간 리뷰 세션 1,891개(일평균 26개)가 쌓였고, review 이력 blob 60.7MB는 `.git` packed blob 바이트의 60%를 차지했다. 더 나쁜 것은 자기증식이다 — 리뷰 산출물이 코드와 같은 브랜치에 커밋되어 한 changeset이 8라운드를 도는 동안, 마지막 라운드 리뷰 프롬프트 94파일 중 86개가 **이전 리뷰 산출물**이었다. 결론(finding)만 레코드로 남기면 이 루프가 끊긴다(D-01·D-07).

7. **원클릭 승인/거절/코멘트** — 거절은 사유 필수. 승인자와 요청자가 같으면 버튼이 비활성화된다("지시자≠승인자", GitHub 패턴). `FR-11 · D-06`
8. **플랜 승인** — 대형 작업 착수 전 게이트. 승인·수정 요청·거절 3분기. Jules가 플랜 리뷰를 1급 게이트로 둔 것과 같은 위치다. `FR-11 · D-06`
9. **자동 사전 검토 결과 인라인** — clemvion의 consistency-check를 플랫폼 서비스로 옮긴 것. 사람이 읽기 전에 기계가 먼저 훑는다. `FR-02 · FR-09`
10. **처리됨 트레일** — 최근 처리 항목이 잠깐 남아 실수를 되돌릴 수 있게 한다. `FR-16`

> **근거 · clemvion 실측** — 승인 지점 자체는 clemvion에도 전부 있었다(merge confirm 2회·conflict patch 승인·e2e 면제·BLOCK 해소). 문제는 전부 **한 사람의 터미널 대화**로 수렴했다는 것이다. 산문 규약만으로 강제한 결과 forced reviewer 미충족이 575 세션 중 160건(28%)에 달했고, checker의 CRITICAL을 `BLOCK: NO`로 하향한 모순도 732건 중 24건(3.3%) 관측됐다. 승인이 **레코드가 있는 수신함 항목**이 되면 이 수치는 측정 가능한 SLA가 된다.

## 3. 공통 상태 표현 규칙

### 3.1 색은 "사람이 지금 무엇을 해야 하는가"로 배정한다

상태 값은 엔티티마다 다르지만 색은 여덟 가지뿐이다. 엔티티별로 색을 따로 정하면 화면을 넘나들 때 학습이 리셋된다. NERV는 **색을 행동 축에 배정**하고 모든 엔티티가 그 축을 공유한다.

| 색 | 의미(행동 축) | SpecVersion | Requirement | Task | AgentSession | severity |
| --- | --- | --- | --- | --- | --- | --- |
| 회색 | 아직 아무 일도 없음 | `draft`, `superseded` | `unimplemented` | `backlog` | `pending` | — |
| 남색 | **사람의 행동 대기** | — | — | `ready` | — | `spec_drift` 태그 |
| 호박 | **검토·응답 대기** | `in_review` | — | `in_review` | `awaiting_input` | `warning` |
| 보라 | 에이전트 점유·수행 중 | — | — | `claimed` | — | — |
| 파랑 | 진행 중 | — | `in_progress` | `in_progress` | — | `info` |
| 초록 | 승인·검증 완료 | `approved` | `verified` | — | `active` | — |
| 청록 | 종료 | — | `implemented` | `done` | `complete` | — |
| 적색 | 차단·실패 | `deprecated` | — | `blocked` | `error`, `stale` | `critical` |

- **색만으로 구분하지 않는다.** 모든 상태 dot에는 텍스트 라벨이 병기된다(`● active`, `○ stale`). 세션 보드처럼 dot이 밀집한 화면에서 색각 이상 사용자가 배제되지 않게 하는 최소 조건이다.
- **`stale`이 적색인 이유**는 세션이 죽었기 때문이 아니라 **클레임이 회수되어 다른 사람의 계획이 바뀌었기 때문**이다. 상태 색은 시스템의 기분이 아니라 사람에게 미치는 영향으로 정한다.

### 3.2 사람과 에이전트 구분

| 맥락 | 표기 |
| --- | --- |
| Task 카드 | `👤 도현`(assignee, 책임) + `🤖 mac-02`(delegate, 실행) 두 줄 병기 |
| 활동 피드 · 감사 로그 | 항목 앞 `👤`/`🤖` 아이콘 + `is_agent` 필드가 필터로 노출 |
| 코멘트 · CR 제안 | 작성자 이름 옆 `AI` 배지 + 위임한 사람 이름을 괄호로(`mac-02/claude-code (도현 위임)`) |
| 승인 버튼 | 에이전트는 승인 액터가 될 수 없다 — 버튼 자체가 렌더링되지 않는다 |

이 규칙의 근거는 세 가지다. Linear는 "에이전트는 책임을 질 수 없다"를 설계 원칙으로 명문화하고 이슈 assignee를 사람에게 유지한 채 에이전트를 `delegate` 필드에 둔다. GitHub는 감사 로그에 `actor_is_agent` 식별자를 추가했고, 에이전트가 만든 PR은 지시한 사람의 승인이 필수 승인 수에 포함되지 않는다. Asana는 AI Teammate가 사용자 권한을 상속하되 절대 확대하지 않는다는 원칙을 전면에 둔다. NERV는 셋을 합쳐 **책임(사람) · 실행(에이전트) · 감사(플래그)** 세 층으로 화면에 고정한다(D-08).

### 3.3 hostname · 에이전트 종류 · 하트비트 표기 규약

| 요소 | 표기 | 규칙 |
| --- | --- | --- |
| 신원 3요소 | `도현 · mac-02 · claude-code` | 넓은 화면은 3단, 좁은 화면은 `mac-02/claude-code`로 축약. hostname은 고정폭 글꼴 |
| 에이전트 종류 | `claude-code` / `codex` / `web` | `web`은 사람이 브라우저에서 직접 하는 행동(에이전트 아님) |
| 하트비트 | `0:12 전` | 상대 시각. 5분 미만 초록 · 5~30분 호박 · 30분 이상 회색+`stale` 배지 |
| 리스 잔여 | `08:04 남음` | 2분 미만이면 호박으로 전환하고 카드가 상단으로 정렬된다 |
| 경과 시간 | `2:31:07` | 세션 시작부터. 비용·타임아웃 판단용 |
| diff 통계 | `+218 −34 · 파일 7` | `+` 초록 `−` 적색. 브랜치명과 함께, 클릭 시 PR |

- 하트비트는 **상대 시각**으로만 쓴다. 절대 시각은 여러 hostname의 시계 차이를 사람이 보정하게 만든다.
- diff 통계 `+N −M` 표기는 클라우드 코딩 에이전트 플랫폼들이 이미 세션 목록의 표준 지표로 쓰고 있다. 낯선 표기를 새로 만들 이유가 없다.
- **hostname이 없으면 세션 카드를 렌더링하지 않는다.** 신원 없는 세션은 P1(스펙 충돌)·P2(중복 작업)를 다시 불러온다.

### 3.4 빈 상태 · 실패 · 오프라인

| 상황 | 화면 |
| --- | --- |
| 받은 요청 비어 있음 | "지금 당신을 기다리는 항목이 없습니다" + 최근 처리 3건 |
| ready 큐 비어 있음 | "ready인 Task가 없습니다 — blocked 3건의 의존성 보기 ▸" (막다른 길 금지) |
| 게이트 판정 실패 | S5·S6 상단 배너 + 연속 카운터. 진행은 허용(fail-open) `D-14` |
| 플랫폼 연결 끊김 | 상단 회색 배너 "오프라인 — 캐시된 읽기 전용. 복구 시 자동 동기화" `NFR-05` |
| 세션 error | 카드 적색 + 마지막 `error` activity 원문 인라인 |
| 권한 없음 | 버튼 비활성 + 툴팁 "이 전이는 `qa`(및 `admin`) 역할만 가능" `FR-14` |

## 4. 인터랙션 노트

### 4.1 승인 카드 — 원클릭 승인/거절/코멘트

- **승인**: 즉시 반영, 카드가 접히고 "처리됨" 트레일에 3분간 남는다. 되돌리기 링크 제공.
- **거절**: 사유 입력이 필수다. 사유는 요청자 알림과 감사 로그 양쪽에 들어간다(FR-16).
- **코멘트**: 상태를 바꾸지 않고 스레드에 남긴다. 질문 카드에서는 선택지 + 코멘트를 함께 보낼 수 있다.
- **지시자≠승인자**: 요청자와 승인자가 같으면 승인 버튼이 비활성화되고 툴팁으로 사유가 뜬다. 에이전트가 제안한 CR은 위임한 사람도 단독 승인할 수 없다.
- **일괄 처리**: 같은 유형·같은 스펙의 저위험 항목만 일괄 승인 가능. 위험도 게이트(D-06)가 저위험으로 분류한 것에 한한다.
- **전달 확인**: 처리 즉시 카드에 "요청 세션 `linux-ci-01/codex`에 전달됨"이 표시되고, 세션 상태가 `awaiting_input → active`로 바뀌는 것이 S5에 반영된다.

### 4.2 세션 카드 — attach · steer · stop

- **attach ↗**: 세션 상세(Activity 타임라인)로 가는 딥링크이자, 로컬 세션이라면 `nerv://session/S-8f31` 형태의 핸드오프 링크다. 터미널 UI들이 `Enter`로 세션에 붙는 조작을 웹에서 재현한 것.
- **steer**: 세션을 멈추지 않고 지시를 큐잉한다. 다음 하트비트/폴링 시점에 에이전트가 수령한다. 스티어링을 1급 동작으로 둔 것은 GitHub mission control과 Linear의 후속 지시 패턴에서 검증된 설계다.
- **stop**: 확인 다이얼로그 + 사유. 이미 푸시된 커밋은 보존되고, 클레임은 즉시 회수되어 Task가 `ready`로 돌아간다.
- **자동 갱신**: WebSocket으로 5초 이내 반영(NFR-02). 연결이 끊기면 배너 + 폴백 폴링, 재연결 시 화면 데이터 재조회.
- **스티어 메시지는 승인이 아니다**: 다른 세션·에이전트가 보낸 메시지는 사람의 승인으로 취급되지 않는다. Claude Code agent teams가 메일박스 설계에서 세운 보안 불변식을 그대로 채택한다(NFR-03).

### 4.3 스펙 diff 뷰 — 버전 diff와 CR 델타

두 가지 diff가 있고 표기를 공유한다.

| 종류 | 진입 | 표기 |
| --- | --- | --- |
| **버전 diff** | S3의 `diff v3..v4` 토글 | 줄 단위 `+`/`−`, 변경 문단 좌측 세로 막대, 헤딩 단위 접기 |
| **CR 델타** | S7 CR 카드 → 델타 전체 보기 | 절 단위 `ADDED / MODIFIED / REMOVED` 카운트 + 변경 절만 렌더링 |

- 기본 뷰는 **변경분만**이다. 전체 문서 보기는 토글로 둔다. 리뷰어가 1,750줄을 처음부터 읽게 만드는 순간 승인은 형식이 된다.
- 코멘트는 diff 뷰에서도 헤딩 앵커에 붙는다. 줄 번호에 붙이면 다음 버전에서 고아가 된다.
- CR 승인 시 영향받는 Task가 재계산되고, 그 목록이 승인 직전 확인 단계에 표시된다(FR-04·FR-05).

### 4.4 커버리지 드릴다운

```text
S2 커버리지 게이지  ─클릭─▶  영역별 목록  ─클릭─▶  Requirement 목록
                                                     │
   REQ-CWC-018  implemented · 검증 증적 없음  ────────┤
   ├ 파생 Task   TSK-9e40 (done) ▸ S4                 │
   ├ PR/커밋     #482 · 9a41c2 ▸ git forge            │
   ├ 리뷰        RVS-5e72 finding 0 ▸ S6              │
   └ 테스트 증적 —            [검증 Task 만들기]  ────┘
```

드릴다운의 끝은 항상 **행동**이다. "증적 없음"에서 멈추지 않고 그 자리에서 검증 Task를 만들 수 있어야 커버리지 숫자가 관리 대상이 된다(FR-13). 이 경로는 QA 페르소나(하나)의 하루에서 가장 많이 쓰인다.

### 4.5 실시간성 · 알림

- **WebSocket**으로 세션 보드·받은 요청 배지·커버리지 숫자를 갱신한다. 목표는 5초 이내(NFR-02).
- **채널 라우팅**: 승인 요청·질문은 즉시(인앱 + Slack), 상태 변화는 다이제스트. 기본값이 다이제스트인 이유는 알림 피로가 승인 품질을 떨어뜨리기 때문이다(FR-12).
- **알림에서 화면으로**: 모든 알림은 처리 가능한 화면의 딥링크를 포함한다. "무슨 일이 있었다"만 알리고 끝나는 알림은 만들지 않는다.

### 4.6 접근성 · 반응형 · 키보드

- 상태는 색 + 텍스트 + 아이콘 3중 인코딩. 색만으로 구분되는 정보는 없다.
- 세션 보드·작업 보드는 좁은 화면에서 카드 스택으로 접힌다. hostname·하트비트·diff는 축약해도 **삭제하지 않는다**.
- 받은 요청은 키보드만으로 처리 가능해야 한다(`j/k` 이동, `a` 승인, `r` 거절, `c` 코멘트). 하루 수십 건을 처리하는 화면이라는 전제.
- 모든 표는 가로 스크롤 컨테이너 안에 있고, 본문이 가로로 밀리지 않는다.

## 5. HTML 파생본 안내

[HTML 파생본](../html/ui-wireframes.html)은 이 문서와 **동일한 내용**을 다르게 렌더링한다.

- S1~S8 전 화면을 `.wf-*` 와이어프레임 킷으로 **실제 UI처럼** 렌더링한다. 아스키 아트의 `(n)` 마커는 화면 안의 번호 배지가 되고, 아래 legend가 그대로 따라붙는다.
- **S3 스펙 상세 · S5 세션 모니터 · S7 받은 요청**은 고충실도로 그린다 — 3열 레이아웃, Activity 타임라인, 델타 미리보기와 선택지 라디오까지.
- IA 트리와 내비게이션 맵은 inline SVG다. 색상은 CSS 변수만 사용하므로 다크 모드에서도 읽힌다.
- 외부 리소스(CDN·웹폰트·외부 이미지·JS 라이브러리)를 쓰지 않는다. 제안서 전체가 파일 복사만으로 열린다.
