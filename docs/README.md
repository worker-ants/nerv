# NERV(가칭) — AI 에이전트 협업 개발 플랫폼 제안서

> **제안서이자 구현 명세다.** 이 문서 세트는 제안으로 시작해 지금은 **구현 중인 코드의 정본**이다 — 지금 어디까지 왔는지는 [구현 현황](#지금-어디까지-왔나--구현-현황)이 답한다.

> **요약** — NERV는 기획자·디자이너·개발자·QA가 하나의 플랫폼에서 **스펙 문서를 단일 진실**로 관리하고, Claude Code·Codex 같은 AI 에이전트를 **MCP·훅·스킬로 연동**해 스펙 작성→검토→구현→테스트를 수행하며, 사람은 **승인/거절/코멘트 게이트**를 지키고 **누구(hostname)의 어떤 에이전트 세션이 무엇을 하는지** 실시간으로 보는 멀티 프로젝트 × 멀티 유저(n:n) 협업 플랫폼이다. 이 제안서는 기존 1인용 하네스(clemvion)의 실측 분석과 웹 딥리서치(도구 생태계·협업 플랫폼·연동 기술·저장 전략·HITL·실전 사례)를 근거로 문제 정의부터 아키텍처·데이터 모델·연동 설계·화면·로드맵까지를 다룬다.

## 지금 어디까지 왔나 — 구현 현황

**이 저장소는 제안서만 있는 곳이 아니다.** 구현이 돌고 있고, 그 사실을 이 문서가 오래 말하지 않았다 — 새로 들어온 사람·에이전트가 "어디까지 됐나" 를 알려면 문서 23편의 변경 기록을 훑어야 했다(2026-09-06 대조).

현황의 정본은 **[4.8 백로그](04-mvp/backlog.md) §1.4** 하나다. 거기에 셋이 있다.

| 무엇 | 어디 |
| --- | --- |
| 에픽별 done / 부분 구현 수 (근거는 파일 경로) | [4.8 §1.4](04-mvp/backlog.md) 에픽 표 |
| **부분 구현의 *남은 것*** — "완료" 로 뭉뚱그리면 남은 절반이 보이지 않는다 | 같은 절 둘째 표 |
| **스토리가 없는 구현** — 만들었는데 백로그에 없는 것 | 같은 절 셋째 표 |

Phase 단위 판정(무엇을 통과해야 다음으로 가는가)은 [3.7 로드맵](03-proposal/roadmap.md) §1.4 의 Go/No-Go 기록 표가 답한다. 단계별 결정과 그 근거는 각 문서 머리의 **변경 기록**에 날짜와 함께 남는다.

> **갱신 규율은 두 자리에 있다.** 규약 쪽은 [AGENTS.md](../AGENTS.md) 문서 작업 규약 6 — *스토리를 끝냈으면 같은 커밋에서 §1.4 를 고친다.* 기계 쪽은 `codebase/scripts/check-backlog-status.mjs` 이고 CI 와 `pnpm preflight` 가 그것을 돌린다(REQ-CB-029). 현황을 사람 손에만 두었더니 "이 문서의 모든 스토리는 현재 `backlog` 다" 가 74개 중 73개에 대해 거짓인 채로 2주를 보냈다.

## 핵심 수치 (전체 문서의 근거 뼈대)

- clemvion `review/`에만 **markdown 13,777개·131MB** — review 이력 blob이 `.git` packed blob 바이트의 **60%**
- **73일간 리뷰 세션 1,891개**(일평균 26개), 커밋 2,464개 중 38%가 review/ 접촉 — 리뷰 산출물이 다음 리뷰의 diff에 포함되는 **자기증식 루프** 실측
- 스펙 동시수정 자동 검출은 **"다른 머신·세션이면 로컬에서 안 보인다"는 이유로 의도적으로 제거**됨(clemvion #576) — 로컬 git 아키텍처의 구조적 상한
- 업계 실측: AI 도입 팀에서 **PR 리뷰 시간 중앙값 +441%, 무리뷰 머지 31%**(Faros AI, 2.2만 명 계측) — 병렬 에이전트의 제1 실패 모드는 리뷰 병목

## 이 문서 세트의 관리 규약 (유지보수용)

- **md가 원본**이고 html은 사람 열람용 파생본이다. 내용 수정 시 둘 다 갱신한다(구조는 `html/`의 사이드바 순서를 따른다).
- **애플리케이션·패키지 코드는 저장소 `codebase/` 하위에, 배포 산출물은 저장소 루트 `deploy/` 하위에** 둔다([4.2 코드베이스와 배포](04-mvp/codebase.md) §1, REQ-CB-015 — 2026-08-22 개정). `docs/`에는 문서와 html 파생본만 들어간다.
- **제품 매뉴얼은 이 문서 세트가 아니다.** 제품을 쓰는 사람을 위한 안내(`/help`)의 정본은 `codebase/apps/web/src/content/manual/<로케일>/<장>.md`이고 **ko·en 두 벌**이며, `docs/`에 사본을 두지 않는다 — 두는 순간 어느 쪽이 정본인지 다시 정해야 한다. 명세는 무엇을 왜 만드는지의 기록이고 매뉴얼은 만들어진 것을 어떻게 쓰는지의 안내다. 화면 명세는 [4.5 화면 명세](04-mvp/screens.md) §2.10, 갱신 규약은 [AGENTS.md](../AGENTS.md) "구현 작업 규약" 5.
- 에이전트(Claude Code·Codex) 작업 규약의 정본은 저장소 루트의 [AGENTS.md](../AGENTS.md)다. `CLAUDE.md`는 그것을 import만 한다 — 어느 머신·세션에서 작업해도 같은 규약이 적용되게 하기 위해서다.
- **결정 번호 D-01~D-14 의 정의문은 그 결정이 논증된 문서에 있다.** 아홉은 1.2 pain-points 에, 다섯은 그 결정을 이끌어낸 조사·분석 문서에 있다 — 3부·4부에 같은 문장이 다시 나오는 것은 **인용이지 정의가 아니다.** **상태값·요구사항 번호(FR/NFR)는 pain-points 가 단일 기준**이고, 그 값들을 한국어와 영어로 **무엇이라 부를지는 [용어 사전](glossary.md)이 정본**이다(2026-09-05 신설 — 그전에는 pain-points 가 "용어 사전을 따른다" 고만 적고 그 사전이 없었다). 화면·매뉴얼·스킬의 말투 규칙(§3)과 영어 규칙(§2.6)도 그 문서에 있다.
