스펙 워크플로우와 거버넌스

NERV의 일은 세 개의 상태 축 — 스펙 문서 축 · 요구사항 구현 축 · Task 실행 축 — 위에서 흐른다(D-02·D-03). 이 문서는 세 축의 상태도와 전이 조건·역할별 권한을 정의하고, 그 위에서 사람이 개입하는 지점을 위험도 가변 게이트(D-06)와 지시자≠승인자 규칙으로 설계한다. 핵심 메커니즘은 scope 겹침 검사(D-04), fingerprint 리뷰 dedup과 게이트 판정(D-07), 그리고 티어·배칭·받은 요청 승격의 알림 설계다.

1. 세 개의 상태 축 (D-02 · D-03)

1.1 왜 축을 나누는가

clemvion에는 상태 축이 하나뿐이다. 스펙 문서의 frontmatter status가 backlog → spec-only → partial → implemented(+archived) 5값을 갖는데, 이건 전부 구현 진행 축이고 문서 자체의 초안·검토·승인 상태가 아니다(clemvion:spec/conventions/spec-impl-evidence.md §3). 그 결과 두 가지 구조적 손실이 실측된다.

① 승인 이력이 사라진다

문서 리뷰 라이프사이클이 없으니 "누가 언제 이 스펙을 승인했는가"는 git PR 어딘가에 묻힌다. 특정 시점의 스펙 상태를 재구성하려면 git 고고학이 유일한 수단이다 — 순수 스펙 135 md · 49,383줄, spec 터치 커밋 857개.

② 상태의 해상도가 문서 단위다

clemvion:spec/5-system/4-execution-engine.md는 1,750줄인데 status 값은 하나다. code: 글로브가 하나라도 매치하면 implemented로 통과하므로 문서 안 개별 요구사항의 누락은 검출되지 않는다.

📊
근거 · 문서 단위 status가 놓친 것

spec이 필수로 약속한 update dedup이 통째로 미구현이었던 사건(요구사항 ID CCH-SE-02, 커밋 2a698f360)은 evidence 가드가 도입된 이후에 발생했다. 요구사항 테이블의 수동 ✅ 마크도 영역별로 131개 대 0개로 갈라져 있다 — 관행은 유지되지 않는다.

✅
설계 결정 D-02 · 스펙 상태는 2축으로 분리한다

① 문서 리뷰 축: SpecVersion draft → in_review → approved → superseded / deprecated ② 구현 축: Requirement 단위 unimplemented → in_progress → implemented → verified. 여기에 실행 단위인 Task 축(backlog → ready → claimed → in_progress → in_review → done, +blocked)이 얹혀 세 축이 된다.

✅
설계 결정 D-03 · 구현 추적의 단위는 Task와 Requirement

"무엇이 구현됐나"는 문서 안 체크박스나 수동 ✅가 아니라 Requirement↔Task↔PR/커밋↔ReviewSession 관계 그래프로 계산한다.

1.2 문서 축 — SpecVersion 상태도

그림 1. 문서 축 — SpecVersion 상태도(D-02 ①). 가변 구간은 draft 하나뿐이다.

SpecVersion은 불변 스냅샷이다. in_review 진입 시점에 본문이 동결되고 content hash가 확정된다. 승인된 버전을 고치는 유일한 경로는 변경 요청(CR)으로 새 draft 버전을 만드는 것이다(3장). 이것이 clemvion의 "latest-only 본문 + 이력은 git" 사상을 계승하면서 사라졌던 승인 축을 되살리는 방법이다.

가변 구간은 문서마다 하나다(2026-09-27 사람 결정). 검토 중인(in_review) 버전이 있으면 새 초안을 만들지 않는다 — 결재가 끝나거나, 거절되어 그 버전이 draft 로 돌아오면 그 위에서 이어 쓴다. 예전에는 열린 초안이 없으면 승인본의 지문과 견줘, 검토 중인 개정판을 건너뛴 초안이 경고 없이 생겼고 개정판이 거절되면 초안이 둘이 됐다. REST(EP-SPEC-08)와 nerv_spec_draft_upsert 가 같은 규칙이다(4.4 REQ-API-200).

옛 버전은 새 초안으로 되살린다(2026-10-15 사람 결정 · 「되돌리기」). 승인본에서 뒤로 가는 전이는 위 상태도에 없다 — 대신 서버가 옛 버전(승인됨 · 대체됨 · 폐기됨)의 본문을 바이트 그대로 복사해 → draft 를 만들고 그 초안은 다른 초안처럼 제출 → 판정 → 결재를 지난다. 열린 초안이 있으면 그 초안을 덮지 않고 거절한다. 규칙과 그 까닭은 §2.4 결정 기록이다(4.4 REQ-API-308).

버린 초안(2026-10-16 사람 결정 D1). 승인본이 있는 문서의 초안은 변경 요청(CR)이 감싼다(§3.5). 그 CR을 거절하거나(planner · admin · 사유 필수) CR을 연 사람이나 초안의 작성자가 철회하면 초안은 지우지 않고 discarded 가 된다. 문서는 승인본 상태로 돌아가고 다음 저장은 새 번호의 초안과 새 CR이다. 버린 초안은 다시 열지 않는다 — 최신 버전 · 기본 보기 · 비교의 기본 양 끝을 고를 때 세지 않고 번호는 다시 쓰지 않는다. 본문이 다시 필요하면 되돌리기로 새 초안을 만든다. 지우지 않는 까닭은 CR이 무엇을 제안했는지가 기록으로 남아야 해서다(4.4 REQ-API-329).

바로 승인(2026-10-11 사람 결정). admin · planner는 초안을 검토 요청과 자기 승인 한 번으로 확정할 수 있다. 새 전이가 아니라 draft → in_review 와 in_review → approved 를 한 트랜잭션에서 차례로 지나는 것이라 두 전이의 가드가 그대로 적용된다 — 사전 검토 block 이면 아무것도 바뀌지 않고, 등급(§2.4)도 그대로라 T3 은 내 승인이 한 자리를 채우고 다른 승인자 한 명을 기다린다. 초안은 가변이므로 사람이 본 지문(content hash)이 필수다(§2.3 다섯째 규칙). 자기 초안이면 §2.3 의 역할 완화로 허용되고 감사에 남는다(4.4 API REQ-API-287).

에이전트는 스스로 승인하지 않는다. 결재 결정(approval:decide)은 어떤 자율성 설정에서도 사람 전용이다 — MCP 사양이 "호스트는 어떤 도구든 호출 전 명시적 사용자 동의를 받아야 한다"고 요구하는 지점이고, OWASP ASI03(Identity & Privilege Abuse) 대응이기도 하다. 2026-10-11 부터 에이전트 세션은 사람이 그 대화에서 대답한 바로 승인을 서버에 전할 수 있다(nerv_spec_approve). 문은 셋이 함께 지킨다 — 호출마다 사람에게 묻는 A3 등급 · 토큰의 옵트인 권한 spec:approve · 사람의 역할(admin · planner). 승인자는 그 사람이고, 결정에는 그 세션이 남는다(4.4 API REQ-API-291).

초안 편집 리스 — 두 개의 편집기가 아니라, 하나의 초안에 대한 두 개의 입력 장치. 기획자는 같은 draft를 웹 에디터(S3)에서도, Claude Code/Codex 세션에서도 쓴다. 이때 두 표면 사이의 동시성은 새 개념이 아니라 D-04의 클레임+리스를 문서 축으로 확장해 푼다 — draft 상태의 SpecVersion 하나당 편집 리스는 최대 1개이고, 보유자는 (사용자, 표면) 쌍이다. 표면은 웹(세션 없음) 또는 에이전트 세션이다.

1.3 구현 축 — Requirement 상태도

그림 2. 구현 축 — Requirement 상태도(D-02 ②). 간선은 파생의 조건이고, 점선은 파생이 되돌리는 경우다 — 검증은 문장이 바뀔 때만 풀린다. 구현 축의 그림은 여기 하나다(2026-09-26).

이 축의 값은 사람이 손으로 찍지 않는다. 서버가 관계 그래프에서 파생한다(D-03).

구현 축의 그림은 여기 하나다(2026-09-26 — 사람 결정 · 구현 축 상태도 검토). 이 그림과 3.3 §1.4 가 거꾸로 가는 간선을 서로 다르게 그리고 있었다 — 여기는 verified → implemented: 회귀 실패, 저기는 implemented → unimplemented: 증적 stale 판정 — 둘 다 첫 커밋 그대로였고, 코드는 어느 쪽도 하지 않았다. 대신 코드는 두 그림에 없는 되돌림 둘을 하고 있었다. 정한 것은 셋이다. ① 구현 축의 상태도와 파생 규칙은 이 절이 정본이고 3.3 은 링크한다(상태 어휘의 정본은 그대로 1.2 D-02). ② 간선은 사건("CR MODIFIED")이 아니라 조건("무엇이 참이면")으로 적는다 — 파생 값에 사건 간선을 그리면 같은 조건을 만드는 다른 길이 전부 빠진다. 그래서 코드가 하던 되돌림 둘(착수 취소 · 새 파생 작업 착수)을 그린다. ③ 증적 stale → unimplemented 는 걷는다 — done 작업이 하나라도 있으면 아래 규칙표는 미구현을 내지 않는다. 낡은 증적은 증적에서 빠질 뿐이다(파생과 커버리지가 이미 거른다 — 그 값을 세우는 것은 지금 임포터의 경로 실존 검사뿐이고(4.7 REQ-IMP-032), 그 증적은 스펙 버전에 붙어 파생에 들지 않는다). 회귀 실패 → implemented 는 서버가 테스트 결과를 받지 않아 판정할 수 없다 — 재검토 트리거: CI 결과를 받게 되면(FR-10 · Phase 2) 최근 실행 결과를 따로 두고 파생의 입력에 넣는다. 요구사항 관리 도구들이 테스트 결과를 최근 실행에서 계산해 워크플로 상태와 따로 두는 것과 같은 모양이다.

verified 의 범위는 커밋이다(2026-10-15 — 4.8 백로그 E15-S03 · 4.4 API REQ-API-315). 2026-09-07 구현은 커밋과 발견을 잇는 축이 없어 그 요구사항에 열린 critical 이 없는지를 봤다. 이제 표가 적은 "커밋 범위" 를 파생 작업마다 그 작업의 최신 커밋을 본 리뷰 라운드로 읽는다 — done 게이트의 커밋 신선도와 같은 커밋 · 같은 비교다(§4.6). 그 라운드에서 관찰된 열린 critical 이 없어야 하고 리뷰가 본 커밋 뒤에 새 커밋이 왔으면 검증되지 않는다. 앞 라운드에 남은 옛 발견은 새 커밋의 깨끗한 라운드를 막지 않는다. 작업의 커밋을 모르거나 그 작업이 리뷰를 받지 않았으면 예전처럼 요구사항 단위로 본다 — 리뷰를 쓰지 않는 프로젝트의 검증은 이 조건 때문에 막히지 않는다. 강등은 여전히 하지 않는다: 이미 verified 인 행은 내리지 않으므로 발견 하나 · 커밋 하나마다 검증 사실이 지워졌다 붙는 일이 없다.

검증 서명은 그 문장에 대한 것이다(2026-09-26 — 사람 결정 · 구현 축 상태도 검토 결정 4·5). 새 버전 승인이 요구사항 문장을 바꿔도 verified 가 그대로 남아, 검증 배지가 아무도 확인하지 않은 문장을 보증했다. 이제 승인이 문장을 바꾸면 그 시각을 남기고(requirement.statement_changed_at — 공백·서식만 바뀐 것은 치지 않는다), 그보다 앞선 서명은 지금 문장을 보증하지 않는 것으로 본다 — 검증이 풀려 implemented 로 돌아가고 다시 검증 필요 가 선다. 이것은 상태가 아니라 표시다: 요구사항 관리 도구들이 위쪽이 바뀌면 아래쪽 링크에 의심 표시를 세우고 사람이 해제하게 하는 것과 같은 모양이다. 해제는 사람만 한다 — qa·admin 이 새 test 증적에 서명하거나, 앞선 테스트가 바뀐 문장에도 맞으면 같은 테스트에 다시 서명한다("영향 없음 확인" — 증적과 이벤트로 남는다). 에이전트가 붙인 test 증적은 서명이 아니다(REQ-API-143). 재작업이 필요하면 그 요구사항에 작업을 붙인다: 그 착수가 위 그림의 implemented → in_progress 다(done 은 되살리지 않는다 · 4.4 REQ-API-190).

clemvion이 CCH-SE-02를 놓친 사각 — "문서는 implemented인데 그 안의 한 요구사항은 미구현" — 은 상태의 단위를 요구사항으로 내리는 것만으로 사라진다.

보관한 작업은 세지 않는다(2026-10-10 — 사람 결정 · 4.4 API REQ-API-286). 보관은 상태를 그대로 두므로, 세면 보관한 in_review 작업이 요구사항을 in_progress에 붙잡고 보관한 backlog 작업이 implemented를 영영 막는다. 작업이 모두 보관됐으면 작업이 하나도 없는 요구사항처럼 손대지 않는다 — 임포트가 정한 값을 중복 하나 보관한 일로 지우지 않는다.

착수하지 않은 재검증 작업은 세지 않는다(2026-10-16 — 사람 결정 · 권장안 A · 4.4 API REQ-API-097). CR 승인은 바뀐 요구사항의 완료 작업마다 재검증 작업을 backlog로 만든다(§3.3 — 아무도 고르지 않으면 기본값이다). 위 표를 그대로 적용하면 그 작업 때문에 「done 이 있지만 아직 전부가 아니다」가 되어 요구사항이 in_progress로 내려가고 qa가 「영향 없음」으로 다시 서명해도 verified로 돌아오지 못한다. §3.3 표는 「재검증 Task 가 착수되면 in_progress」라고 적어 두 곳이 어긋났고 코드는 이 표를 따랐다 — §3.3의 문장을 정본으로 본다. 재검증 작업은 다시 확인할지를 사람에게 묻는 작업이라서, 아무도 시작하지 않은 동안 요구사항의 구현 상태를 바꾸면 qa의 재서명을 막는다. 그래서 재검증 작업(task.reverifies_task_id로 그 작업이 다시 보는 완료 작업을 가리킨다 · 4.3 REQ-DB-053)이 backlog · ready · blocked이고 클레임된 적이 없으면 위 표의 어느 줄에도 세지 않는다. 착수는 클레임이다 — 클레임된 적이 있으면(풀어서 ready로 돌아왔어도) 다른 작업과 똑같이 세고 그 착수가 그림의 implemented → in_progress다. 보관한 작업을 세지 않는 규칙과 같은 자리에 둔다. 택하지 않은 안은 둘이다 — qa의 재서명이 재검증 작업을 닫는 것은 명세에 없는 동작이고 기본값에서 재검증을 빼는 것은 같은 날 정한 기본값(§3.3)을 뒤집는다.

작업이 없는 요구사항은 임포트 값을 그대로 두고 출처를 보인다(2026-10-15 — 사람 결정). 보관하지 않은 작업이 하나도 없는 요구사항은 파생할 재료가 없어 서버가 값을 바꾸지 않는다. 임포트가 문서에서 읽어 넣은 값(clemvion 의 implemented 들)을 unimplemented 로 덮으면 이관한 팀의 현황이 하루아침에 0 이 된다. 대신 그 값이 파생한 값이 아니라는 사실을 화면 · API 에 「출처: 임포트」로 표시한다. D-03(사람이 손으로 찍은 표시를 믿지 않는다)의 뜻은 값을 지워서가 아니라 값이 어디서 왔는지 보여서 지킨다 — 숫자를 그대로 보고하면서도 파생한 값과 구별된다. 3.7 로드맵 §4.4 의 성공 기준 2-8 은 파생한 요구사항의 비율과 임포트 값으로 남은 요구사항의 수를 함께 보고한다. 남은 요구사항마다 검증 작업을 만드는 안은 M2 컷오버 때 clemvion 팀과 정한다. 구현은 4.8 백로그 E15-S02 다.

1.4 Task 축 — 실행 상태도

보관은 상태가 아니다(2026-10-10 — 사람 결정 · 4.4 API REQ-API-284). 진행하지 않기로 한 작업은 이 그림의 어느 상태에서든(done은 빼고) 보관한다. 상태는 그대로 두고 표시(task.archived_at)만 남긴다 — 보관한 작업은 목록 · 작업 큐 · 클레임 · 의존 · 구현 현황에서 빠지고, 사람이 복원하면 그 상태로 돌아온다. 상태 어휘를 늘리지 않은 이유는 보드 레인 · 전이 표 · 구현 축이 모두 상태를 보기 때문이다.

그림 3. Task 축 상태도. blocked는 별도 축이 아니라 어느 상태에서든 드나드는 예외 상태다.

그래프 자체는 강제하지 않는다(3.3 데이터 모델 §2.4 · 2026-09-02 결정). 강제하는 것은 문지기 여덟이다 — 어휘 · 담당자 · 리스 만료 · done 최종 · 세션의 리스 구속 목표 셋(in_progress·in_review·done) · ready 판정(4요소·의존) · claimed 는 클레임으로만 · 활성 클레임이 걸린 ready·backlog 는 해제 먼저(4.4 API 명세 REQ-API-129~132 — 뒤의 넷이 2026-09-07 에 섰다). 문지기를 늘린 것이지 경로 그래프를 강제하기로 바꾼 것이 아니다.

blocked 진입 시 사유 코드(awaiting_answer / dependency_broken / spec_conflict / external)를 필수로 받는다 — clemvion의 (unstarted) sentinel이 "placeholder는 어떤 worktree와도 매칭되지 않아 plan이 게이트에서 사라진다"는 이유로 가드에 거부당한 것과 같은 원리다. 사유 없는 blocked는 백로그 부패의 씨앗이다.

해소 조건은 받지 않는다 — 파생한다(2026-09-06 결정 · REQ-API-118). 이 문장은 오래 "사유 코드와 해소 조건을 필수로 받는다" 였는데, 해소 조건을 담을 열이 만들어진 적이 없다. 만들지 않기로 했다: 사유마다 해소 원천이 이미 저장에 있기 때문이다 — awaiting_answer 는 question.task_id, dependency_broken 은 task_dependency, spec_conflict 는 rebrief_required_at. 열을 하나 더 두면 같은 사실에 포인터가 둘이 되고 둘은 언젠가 갈라진다(기준선/베이스라인 165곳이 그 자국이다). 게다가 그 열은 넷 중 하나에만 맞고 나머지 셋에는 NULL 이 들어간다 — 넷 중 셋이 비는 열은 계약이 아니라 흔적이다. 서버는 EP-TASK-04 응답에 blocked_resolution 을 파생해 실어 준다(satisfied · pending[]). external 은 저장소 밖이라 파생할 원천이 없고, 그때 satisfied 는 false 가 아니라 null 이다 — "아니다" 와 "서버가 판정할 수 없다" 는 다른 말이다.

파생이라 얻는 것이 하나 더 있다. blocked_reason 은 아무도 자동으로 지우지 않아서, 선행 의존이 done 이 되어도 사람이 손으로 전이를 다시 눌러야 풀린다. 파생값은 그 순간 satisfied: true 가 되므로 화면이 "이제 풀 수 있습니다" 를 말할 수 있다 — 자동 해소로 가는 길이 여기서 열린다.

발견 코멘트는 참여다(2026-10-11 — 사람 결정 · 4.4 API REQ-API-294). 발견에 말을 남기는 일(EP-REV-05)이 처분과 같은 review:resolve를 요구해서 developer · designer는 자기 코드에 달린 발견에 답하지 못했다. 스펙 코멘트는 처음부터 "권한이 아니라 참여"로 보고 viewer까지 받는다. 같은 원칙으로 발견 코멘트를 review:submit(viewer를 뺀 모든 역할)으로 낮추고 처분은 그대로 둔다 — 대화는 참여이고 결정은 권한이다. 에이전트 토큰도 review:submit이 있으면 코멘트한다. 리뷰 루프에서 해명을 남기는 데 쓸모가 있어 막지 않는다.

발견 처분은 admin · planner · qa의 것이다(2026-10-11 — 사람 결정). 이 표는 오래 designer · developer에게도 「finding 해결 판정」을 ● 로 적었다. 실물은 처음부터 review:resolve(admin · planner · qa)만 받았고(4.4 API EP-REV-02 · 화면도 같다), 2026-09-07에는 발견 코멘트의 권한을 문서가 코드에 맞춘 적이 있다. 표를 실물에 맞춘다. 코드를 표에 맞추는 안(developer · designer에게 처분을 연다)은 택하지 않았다 — 자기 코드에 달린 발견을 스스로 닫을 수 있게 되면 리뷰의 뜻이 약해진다. developer · designer는 코멘트로 답하고(위 단락) 처분은 qa · planner가 한다.

📊
근거 · 역할 분리는 계승, 강제 수단은 교체

clemvion은 역할을 경로별 쓰기 권한으로 구현했다(planner는 spec/**, developer는 codebase/**이고 spec/은 read-only). 분리 자체는 계승할 자산이지만 강제 수단은 SKILL.md 산문("절대 수행하지 않으며")이었다 — 훅이 막는 것은 "어디서·무엇을 안 하고 push하는가"이지 "누가"가 아니다. NERV에서는 같은 분리가 서버 인가로 강제된다.

결정 기록(2026-09-28 · 사람 결정 — 리뷰어 지정은 역할 큐로 충분하다). 결재는 특정인을 지정하지 않고 역할 큐로 간다. approval.assignee_role 이 있으면 그 역할의 멤버가, 없으면 결정 권한(approval:decide)이 있는 역할의 멤버 누구나 받는다. 몇 명이 승인해야 하는지는 게이트 티어의 정족수가 센다(§2.4). 위 표의 "자동 추가 규칙"(워처 등록 · 영역 오너 통지)은 만들지 않는다. approval.assignee_user_id 는 특정인에게 맡기는 자리로 스키마에 남지만 지금 채우는 곳은 없다. 다시 볼 때: 같은 역할의 사람이 많아 받은 요청이 서로 미루는 일이 생기면 특정인 지정(영역 오너 먼저)을 검토한다.

재검토 조건을 숫자로 정한다(2026-10-15 · 사람 결정 — 결재를 특정인에게 맡기기, 권장안 A). 역할 큐를 그대로 둔다. "서로 미루는 일"을 재는 지표는 최근 30일에 요청된 결재 가운데 2회째 리마인더(T+1d)까지 간 비율이다. 분모는 그 창의 결재(면제 제외) 가운데 결정됐거나 2회째 리마인더까지 간 것이고 하루가 안 된 결재는 아직 어느 쪽인지 몰라 세지 않는다. 이 비율이 30%를 넘으면 재검토한다. 기준 30%와 창 30일은 이번에 정한 시작값이고 조정할 수 있다(ROLE_QUEUE_REVIEW_THRESHOLD · ROLE_QUEUE_REVIEW_WINDOW_DAYS). 프로젝트 개요가 비율을 보이고 기준을 넘으면 재검토 안내를 덧붙인다(4.4 API REQ-API-307 · 4.5 화면 명세 REQ-WEB-311). 재검토하면 다음 단계는 사람 지정(B) 이다 — 자동 지정(C)이 아니다. assignee_user_id를 채우는 길은 사람이 승인자를 고르는 데서 시작한다. 위의 "다시 볼 때"는 이 조건으로 바뀐다. T+1d 대체 승인자 후보(§2.6)도 이때 함께 정한다(2026-10-15 · 사람 결정 A) — 결재가 역할 전체에 가는 동안에는 후보로 보여 줄 사람이 이미 알림을 받은 사람이라, 고르는 규칙은 사람 지정과 한 번에 정하는 편이 맞다.

2.3 지시자 ≠ 승인자

GitHub는 Copilot이 만든 PR에 대해 "작업을 지시한 사람의 승인은 필수 승인 수에 포함되지 않는다"고 못 박고, 에이전트가 푸시한 변경의 CI는 사람이 diff를 확인하고 "Approve and run workflows"를 눌러야 돈다. NERV는 이 규칙을 스펙 승인까지 확장한다.

승인 유효성 판정 (서버)
  reject IF actor_id == approval.requested_by            # 본인이 낸 요청을 본인이 승인
  reject IF actor_id == spec_version.author_user_id      # 초안 작성자 = 승인자
  reject IF actor.is_agent                               # 에이전트는 영구 불가
  reject IF actor_id == agent_session.owner_user_id      # 에이전트를 지시한 사람 = 승인자
         AND spec_version.author_session_id IS NOT NULL
  reject IF approval.target_content_hash != spec_version.content_hash   # stale 승인

네 번째 규칙이 D-08의 귀결이다. 에이전트는 소유 사용자의 위임 권한으로 행동하므로, 에이전트가 쓴 초안을 그 소유자가 승인하면 실질적으로 자기 승인이 된다. UI는 이 경우 승인 버튼을 비활성화하고 "이 초안은 당신의 세션이 작성했습니다 — 다른 승인자가 필요합니다"를 표시한다.

다섯 번째 규칙은 승인의 유통기한이다. 승인은 특정 content hash에 대한 결정이므로 대상 본문이 바뀌면 무효화되고 재요청된다. 승인 감사 레코드에는 승인 ID·시각·요청자·승인자·대상 리소스·판정 근거·결정·실행 결과를 남긴다 — 사후에 "그때 왜 자동 승인됐나"를 재구성하려면 그 판정이 어느 정책으로 났는지 반드시 알아야 한다. 정책 버전 대신 적용 정책 지문을 남긴다(2026-10-15 사람 결정). 판정 근거는 티어 · 점수 · 축별 점수 · 신호 · 축 산출에 넣은 값과 그 판정에 쓴 유효 정책(기본값까지 채운 정책)의 지문이다. 지문은 그 정책을 키 정렬한 JSON 의 sha256 앞 16자다. 버전 번호는 누군가 올려야 하고 올리지 않은 수정은 같은 번호로 다른 판정을 내지만 지문은 내용에서 나와 잊을 수 없다. 정책을 고칠 때의 감사(project.updated)가 같은 지문과 정책 본문을 함께 남기므로 지문으로 본문을 찾으면 그때의 판정을 다시 계산할 수 있다. 판정은 제출 때 한 번이고 승인 이벤트는 제출 때의 지문을 그대로 기록한다(§2.4 ④). 이벤트의 모양은 4.4 API §2.1a · REQ-API-303이 정본이다.

자기 승인 금지. 위 판정 규칙을 정책 한 문장으로 못 박으면 이렇다 — 에이전트가 작성한 초안(spec_version.author_session_id가 NOT NULL)은 그 세션을 소유한 사용자가 단독으로 승인할 수 없고, 다른 멤버 1인 이상의 승인이 필요하다. T0(자동 통과 티어)는 예외다 — 기존 규칙대로 자동 통과한다(§2.4). GitHub가 Copilot PR에 적용한 "지시자≠승인자" 규칙을 스펙 승인으로 확장한 것이며, 1차 출처는 2.3 협업 플랫폼의 에이전트 통합에 있다.

소규모 완화. 프로젝트 멤버가 2인 미만이거나 승인 가능한 다른 역할이 없으면 이 정책은 자동 완화된다 — 차단 대신 승인 화면에 배너를 띄우고 감사 이벤트를 기록한다(D-14의 fail-open+관측+격상 패턴 재사용). clemvion 1인 마이그레이션(D-12)이 이 규칙에 막혀 죽지 않기 위한 조항이다. 정책은 S8 게이트 정책에 토글로 노출된다(기본 ON).

역할 완화(admin 2026-08-30 · planner 2026-10-11 사람 결정). admin · planner는 자기 결재 — 자기가 요청했거나 · 썼거나 · 자기 세션이 쓴 초안 — 를 승인할 수 있다. 기획자가 자기 세션이 쓴 초안을 그 자리에서 승인하는 것이 이 플랫폼의 주 경로라서다. 허용하는 것과 감추는 것은 다른 일이라 결정 이벤트에 self_approved 가 남는다. 결재가 직군 자리(designer · qa · developer)이면 이 완화는 적용되지 않고, 정족수의 "서로 다른 사용자"(T3)는 역할과 상관없이 그대로다 — 한 사람이 두 자리를 채우지 못한다(4.4 API REQ-API-288).

2.4 위험도 가변 게이트 (D-06)

✅
설계 결정 D-06 · 사람 개입 게이트는 위험도 가변

표준 게이트 4+1: ① 스펙/CR 승인 ② 플랜 승인(대형 작업 착수 전) ③ 에이전트 질문(awaiting_input) ④ PR 머지·CI 실행("지시자≠승인자" 채택) + ⑤ 게이트 면제는 기록되는 BYPASS. 저위험 변경(오탈자 등)은 자동 통과 경로를 둬 "버그 하나에 16개 AC" 워터폴 비판을 제품으로 반박한다.

게이트가 본문을 읽는다(2026-09-02 — 정합 점검). 구현은 요구사항 추가·삭제를 상수 0 으로 넘기고 '수정' 만 requirement 행의 존재로 근사하고 있었다. 그런데 그 표를 채우는 것은 임포터뿐이라, 에이전트가 쓴 스펙에는 행이 하나도 없다 — 신규 feature 스펙이 부작용 0 + 민감도 1 = 1점 → T0 이 되어 사람이 한 번도 보지 않고 approved 로 갔다. 이제 현재 approved 본문과 견줘 추가·수정·삭제를 센다.

두 결정이 내려졌다(2026-09-02 · 사람 확정).

① 첫 승인 버전은 티어를 한 단계 올린다. 위 표의 T2 예시가 "신규 feature 스펙"인데 축으로 계산하면 3점(T1)이었다 — 예시와 축이 어긋났고, 어긋난 쪽으로 실물이 돌아 요구사항을 새로 세우는 문서가 사람 없이 approved 로 갔다. 축을 고치지 않고 동적 강화 신호(firstApprovedVersion)로 둔다: 축은 변화의 크기를 재는 자이고 "처음 들어오는 약속"은 크기가 아니라 성질이라, 축에 가산점을 섞으면 그 자가 무엇을 재는지 흐려진다. 가산은 문서당 한 번이고, dynamic_escalation 을 끈 프로젝트에서는 붙지 않는다. 경계값을 낮추는 선택지는 택하지 않았다 — 3점짜리를 전부 T2 로 올리면 문구 수정까지 승인 대기에 걸리고, 대기가 늘면 사람이 카드를 읽지 않고 누르기 시작한다(OWASP ASI09 의 consent fatigue).

② T1 의 이의제기 창은 걷는다. 구현이 없었고(값을 산출만 하고 아무도 읽지 않았다), ①로 위험한 문서가 T2 로 올라간 뒤로 T1 에 남는 것은 기존 문서의 문구 수정 정도다. gate_policy.t1_objection_hours 키는 제거했고 저장된 값은 마이그레이션 0016 이 지운다. T0 과 T1 의 동작은 같다 — 남는 차이는 감사 기록의 등급뿐이다.

곁가지로 정책이 장식이 아니게 됐다. tier_boundaries 와 dynamic_escalation 은 화면에서 고칠 수 있는데 판정이 상수를 쓰고 있었다(2026-09-02 정정). 고칠 수 있고 효과가 없는 값이 화면에 있으면, 그것을 고친 사람은 게이트를 조인 줄 안다.

이 티어는 스펙 변경 게이트 티어(T0~T3)이며, 3.4 에이전트 연동 설계가 정의하는 도구 호출 위험도(A1~A4)와는 다른 축이다.

반사적 승인 방지

모든 것을 묻는 설계는 consent fatigue를 낳고, 이것이 OWASP ASI09가 지목하는 취약점이다. 그래서 승인 카드는 요약문이 아니라 실제 diff와 대상 리소스 원문을 먼저 보여준다(§6.4).

재시도 신호를 정의하고 롤백 신호를 걷는다(2026-09-26 — 사람 결정 · 동적 강화 두 신호 검토). 이 절은 오래 "같은 Task 에서 재시도가 임계를 넘거나, 최근 30일 내 해당 영역의 승인 후 롤백 이력이 있으면 +1" 이라 적었는데, 무엇을 셀지 정해진 적이 없어 서버는 둘 다 세지 않았다. ① 같은 실패 3회 신고 — 서버는 테스트 결과를 받지 않으므로(증적에 통과·실패 열이 없고 웹훅은 PR·커밋의 존재만 적는다) 실패를 직접 세지 않고, 에이전트가 e2e-fail-3x 로 올린 에스컬레이션(질문의 escalate · 발견 처분의 escalate_reason)을 센다. 한 건이면 선다 — 임계 3 은 어휘 안에 있다. 신고가 제출에 닿는 길은 셋이다: 그 스펙을 가리키거나 · 그 스펙에서 파생된 작업의 것이거나 · 제출한 세션의 것. 사람이 그 스펙을 마지막으로 승인한 뒤의 신고만 센다 — 사람이 승인했으면 본 것이고, 자동 통과는 아무도 보지 않았으므로 창을 닫지 않는다. infra(환경 탓)와 sensitive-fix(민감도)는 실패가 아니라 세지 않는다. 카드는 신호 곁에 그 신고로 가는 링크를 단다(4.4 REQ-API-189 · 4.5 REQ-WEB-240). ② 롤백 이력은 걷는다 — "승인 후 롤백" 에 해당하는 전이가 NERV 에 없다: 승인된 문서에서 뒤로 가는 전이가 없고, 과거 버전 복원은 새 버전을 만드는 일이며 그 기능도 아직 없다. 재검토 트리거: 버전 되돌리기를 만들거나 승인 뒤의 되돌림이 실측되면, 되돌림 버전이 승인된 문서의 가장 가까운 area 조상 아래에서 다음 제출에 30일 동안 서는 신호로 켠다. ③ 여럿이어도 한 단계다 — 신호가 요구하는 것은 사람이 한 번 보는 것이지 두 사람이 아니다. 쌓으면 첫 버전인 T1 문서에 신호 하나가 겹쳐 T3(직군 교차 2인 + 파생 작업의 플랜 승인)까지 갔다. ④ 판정은 제출 때 한 번이고, 승인 때의 기록은 그 판정을 옮겨 적는다 — 다시 계산하면 그 사이의 변화가 기록의 티어만 바꿔 슬롯과 어긋난다.

축소 신호를 더한다 — 최소 T2(2026-10-09 — 사람 결정). 제출한 버전이 계보의 직전 버전보다 크게 줄었으면(크기 · 제목 수 · 남은 요구사항 가운데 하나가 절반 아래 — 4.4 API REQ-API-270의 판정) body_shrunk 신호가 선다. 확인 없이 줄었으면 사전 검토(base-continuity)가 제출을 막는다. 그래서 여기까지 오는 것은 저장할 때 allow_shrink로 의도한 삭제라고 밝힌 버전이다. 계기는 clemvion 용어 사전 v4다 — 34.7KB 본문이 484바이트가 된 채 T3로 승인됐다. 그 사고는 이미 가장 높은 등급이라 신호로 막을 수 없었다. 남은 빈틈은 반대쪽이다: 확인한 축소가 T0 · T1이면 아무도 보지 않고 승인된다. 그래서 이 신호만 바닥이 있다 — 한 단계 뒤에도 T0 · T1이면 T2로 올린다. 한 단계만 올리면 요구사항 없는 design 문서(1점 · T0)가 T1이 되어 여전히 자동 통과한다. T2 · T3에서는 다른 신호와 같이 한 단계다. 여럿이어도 한 단계다(위 ③). 기존 두 신호에는 바닥을 두지 않았다 — 같은 한계(T0 문서의 첫 승인 버전은 T1로 자동 통과)가 있다. 그러나 그것을 바꾸는 것은 2026-09-02 · 09-26 결정을 다시 여는 일이라 이번 범위 밖이다. dynamic_escalation을 끈 프로젝트에서는 세지 않는다.

결정 기록 — 과거 버전을 되살리기(2026-10-15 · 사람 결정 · 권장안 B). 서버가 옛 버전(승인됨 · 대체됨 · 폐기됨)의 본문을 바이트 그대로 복사해 새 초안을 만들고 그 초안은 보통 게이트(제출 → 판정 → 결재)를 지난다. 승인본을 직접 되돌리지 않는다 — 문서 축(§1.2)에 승인본에서 뒤로 가는 전이가 없고, 그런 전이를 두면 이 절의 게이트(D-06)를 건너뛴다. 옛 본문을 읽어 손으로 다시 저장해도 같은 본문은 되지만 어느 버전을 되살렸는지가 남지 않았다. 이름은 「되돌리기」(영문 revert)다 — 「복원」은 보관한 문서를 되살리는 말이고 「이 버전에서 파생」은 작업을 만드는 말이라 겹치지 않게 했다(용어 사전 §2.2). 결정에 없던 세부 셋은 이번에 정한 기본값이고 사람이 다시 정할 수 있다. ① 열린 초안이 있으면 거절한다 — 덮으면 남의 작업이 조용히 사라진다. 응답이 그 초안의 번호를 알려 주고, 그 초안을 이어 쓸지 옛 본문으로 바꿀지는 사람이 정한다. 검토 중인 버전이 있으면 초안 저장과 같은 거절이다(§1.2). ② 크게 줄어도 받는다 — 되살리는 것은 사람이 고른 일이라 allow_shrink를 따로 묻지 않고 그 확인을 버전에 남긴다. 위 축소 신호는 그대로 판정에 들어가 최소 T2가 된다. ③ 권한은 새 초안을 만드는 것과 같다(§1.2 표 → draft). 새 버전은 되살린 옛 버전의 번호(reverted_to_version_no)를 남기고 저장 · 제출 · 승인 이벤트가 같은 값을 기록한다(4.4 API REQ-API-308). 웹은 본문을 쓰지 않으므로 버전 기록의 옛 버전 보기에 에이전트에게 맡길 명령을 보인다(4.5 화면 REQ-WEB-312).

점화 기록 — 롤백 신호(2026-10-15). 위 2026-09-26 결정 ②의 재검토 트리거 "버전 되돌리기를 만들면"이 이 결정으로 점화됐다. 이번에는 신호를 더하지 않는다 — 게이트를 무겁게 하는 일이라 사람이 정한다. 계산할 재료만 남긴다: 버전 행의 reverted_to_version_no와 제출 · 승인 이벤트의 같은 값이다. 더할지는 아래 결정 기록(2026-10-15)대로 실측을 보고 정한다.

결정 기록 — 롤백 신호는 실측 뒤에 정한다(2026-10-15 · 사람 결정 · 권장안 A). 위 점화 기록이 남긴 결정이다. 지금은 롤백 신호를 게이트에 더하지 않는다. 되돌린 버전 번호(spec_version.reverted_to_version_no)가 이미 버전 행과 제출 · 승인 이벤트에 남으므로, 되돌리기를 실제로 어떻게 쓰는지 재고 그 결과로 정한다. 그때까지 되돌림 버전에는 기존 신호(축소 신호 등)만 적용된다. 지표 화면은 만들지 않는다 — 셀 일이 생기면 버전 행에서 센다. 재검토 트리거: 한 프로젝트에서 ① 최근 30일에 승인된 버전 가운데 되돌리기로 만든 버전(reverted_to_version_no 가 있는 것)이 10%를 넘거나, ② 되돌리기로 만든 버전이 승인된 뒤 30일 안에 같은 문서에서 다시 되돌리기가 일어나면(한 번이라도) 롤백 신호를 다시 검토한다. 창 30일은 역할 큐 재검토(§2.2 · ROLE_QUEUE_REVIEW_WINDOW_DAYS)와 같은 값이고 기준 10%는 이번에 정한 시작값이라 조정할 수 있다. 다시 검토할 때의 안은 2026-09-26 트리거가 적어 둔 것이다 — 되돌림 버전이 승인된 문서의 가장 가까운 area 조상 아래에서 다음 제출에 30일 동안 적용되는 신호.

T+2d 지연과 T+7d 만료는 아래 결정대로 집행한다. 모든 단계는 라운드마다 한 번이다 — 다시 제출하면 남은 자리의 요청 시각이 그 제출로 바뀌고 앞선 라운드의 리마인더 · 지연은 세지 않는다.

결정 기록(2026-10-15 · 사람 결정 — 결재 만료 · 에스컬레이션, 권장안 A). ① T+7d 만료. 스펙 결재가 7일 동안 결정되지 않으면 서버가 그 버전을 in_review → draft로 되돌린다. 거절과 같은 전이이고 같은 라운드 규칙이다 — submitted_at을 비우므로 다시 제출하면 T3에서 이미 채워진 승인은 세지 않는다. 결재 행에는 결정을 쓰지 않는다. 결정은 사람의 것이고 결정 어휘(§2.5)도 늘리지 않는다. 만료라는 사실은 approval.expired(대상은 그 버전 · 라운드마다 한 번)가 남기고 요청자에게 보통 알림이 간다. 그 요청의 알림은 읽음이 되고, 기다리던 세션은 깨어나 하트비트로 approval_expired를 듣는다. 만료된 자리에 뒤늦게 온 결정은 거절한다. 만료가 없던 동안에는 검토 중인 버전이 남아 새 초안 저장이 막혔다(§1.2 "가변 구간은 문서마다 하나"). ② T+2d 에스컬레이션은 알림을 받지 못한 사람에게만 보낸다. 기본 큐 결재는 admin · planner가 이미 요청과 리마인더를 받는다(§6.3 구현 범위). 같은 사람에게 알림을 하나 더 보내는 대신 받은 요청 카드와 프로젝트 개요에 "지연"을 표시한다. 직군 자리(qa · designer · developer) 결재는 그 역할 멤버만 알림을 받으므로, 결정할 수 있는 admin(그 역할을 겸하지 않은 사람)에게 중요 알림을 보낸다. 결재마다 한 번이다. ③ 돌아갈 초안이 없는 결재는 만료하지 않는다(이번에 정한 기본값). 계획 승인과 critical 하향 결재는 되돌릴 상태가 없어 에스컬레이션만 하고 "지연" 표시가 남는다. 이 기본값은 사람이 다시 정할 수 있다. ④ 받은 요청의 만료 상태는 결정 없이 끝난 결재의 탭이다(§6.4).

결정 기록 — T+1d 대체 승인자 후보는 미룬다(2026-10-15 · 사람 결정 A). 위 표에만 있고 후보를 고르는 규칙이 없다. 결재는 지금 역할 전체에 간다(§2.2) — 기본 큐면 admin · planner 모두가, 직군 자리면 그 역할의 멤버 모두가 요청과 리마인더를 이미 받는다. 그래서 후보로 보여 줄 사람이 곧 이미 알림을 받은 사람이고 화면에 이름을 하나 더 띄워도 결정할 사람은 늘지 않는다. 역할 큐 재검토 지표(최근 30일에 2회째 리마인더까지 간 비율)가 30%를 넘어 재검토할 때 사람 지정(B)과 함께 정한다 — 특정인에게 맡기는 길이 생겨야 "그 사람 대신 누구" 라는 후보에 의미가 생긴다.

awaiting_input으로 사람을 기다리는 에이전트 세션은 이 SLA와 별개로 하트비트를 유지한다(D-13). 승인이 며칠 걸려도 세션은 죽지 않아야 하며, 이는 "리뷰가 오래 걸리면 상태를 직렬화해 저장하고 나중에 재개하라 — 그것은 여전히 같은 run이다"라는 에이전트 승인 설계의 정석과 같다. 반대로 에이전트가 응답하지 않는 경우는 무활동 30분에 stale로 자동 전이하고 클레임을 회수한다(§4.5).

3. 변경 요청(CR) 흐름 FR-04

3.1 왜 CR인가

approved SpecVersion은 불변이다. 요구공학에서 승인된 요구사항 집합을 baseline으로 두고 이후 변경을 변경 통제로 다루는 것과 같은 이유 — 승인 시점의 약속이 나중에 조용히 바뀌면 승인 자체가 무의미해진다. clemvion은 이 계층이 없어 본문을 직접 고치고 이력을 git에 위임했고, 그 결과 "정정/어긋/틀렸/누락" 류의 사후 정합화 커밋이 상시 업무가 됐다(docs(spec) 커밋 211개).

3.2 델타 뷰

CR은 새 draft 버전 + 요구사항 단위 델타를 함께 제시한다. 리뷰어는 1,750줄 본문 전체가 아니라 델타만 본다.

게이트 티어: T3 (부작용 2 · 민감도 1 · 가역성 2 · 범위 1 = 6)

이 델타 어휘(ADDED/MODIFIED/REMOVED)는 파일 기반 SDD 도구들이 델타 스펙으로 검증한 형태이고, NERV에서는 파일 diff가 아니라 요구사항 ID 단위로 계산된다는 점이 다르다.

CR의 표시 키는 작업과 같은 형식의 <PRJ>-C-XXXXXX 다(2026-10-16 사람 결정 D2 · 3.3 데이터 모델 §5.1). 화면은 /p/:proj/crs/:cr 이고 델타는 CR이 감싼 두 버전(승인본과 그 초안) 사이만 보여 준다 — 버전을 고르는 비교 화면과 같은 diff를 쓰되 양 끝이 고정이다(4.5 화면 명세 §2.4f).

진행 중인 클레임이 있는 요구사항을 MODIFIED/REMOVED 하는 CR은 그 세션에 즉시 알림을 보내고, 세션은 다음 하트비트에서 변경을 인지해 blocked(spec_conflict)로 스스로 전이할 수 있다. clemvion이 "동일 spec 파일을 두 worktree가 동시 수정 중이면 plan에 명시하고 직렬화한다. 자동 검출은 없다"고 포기했던 지점(clemvion:.claude/docs/worktree-policy.md §3)이 여기서 복원된다 — 서버가 모든 세션의 scope 선언을 보기 때문이다.

재브리핑 플래그의 수명. 서버가 세운 rebrief_required_at은 자동으로 사라지지 않는다 — 사람이 위임 명세 4요소를 새 버전 기준으로 재확인하고 Task의 기준 버전(source_spec_version_id)을 최신 approved로 갱신하는 순간 해제된다. 재브리핑 전까지 세션의 구현 컨텍스트는 기존 기준 버전이다 — 서버가 조용히 최신 버전을 먹이는 일은 없다(에이전트 연동 설계 §2.4 기준 버전 규약). S4 카드에는 재브리핑 배지가 뜬다(4.5 화면 명세).

기준선으로 개발하는 작업은 재브리핑하지 않는다(2026-09-27 사람 결정 · 4.4 REQ-API-210). 작업에 기준선이 있으면 "그 세트로 개발한다" 가 약속이라, 기준 버전만 최신 approved 로 옮기면 대상 문서는 지금 것이고 주변 문서는 옛 세트가 된다. 그래서 승인이 그런 작업에 재브리핑 플래그를 남기지 않고, 재브리핑 요청은 거절된다. 세트를 옮기려면 사람이 작업의 기준선을 새 기준선으로 바꾼다 — 기준 버전도 그 세트의 핀으로 함께 간다(§3.6).

참조 문서 전파(문서 간 영향). 위 표는 같은 문서 안의 Requirement·Task까지만 움직인다. 문서 A의 새 버전이 승인되면 서버는 spec_relation의 역방향 — A를 references/depends_on/duplicates로 참조하는 문서들 — 을 재검토 후보로 산출해 문서마다 spec.recheck_requested 이벤트를 한 번 만들고(§6.3, 대상 문서 owner_role에게 standard 알림 · 관계 종류가 여럿이어도 한 번이고, 행위자는 승인한 사람이라 그 사람은 받지 않는다 · 2026-09-27), 그 문서의 S3 상태 패널에 "참조 스펙에 앞선 버전 존재" 배지를 표시한다. clemvion의 "네 문서가 각자 필드를 열거"·"모방한 쪽이 맞고 원본이 틀렸다" 사고의 재발 방지 장치다. 승인 트리거로 cross-spec 검사기(§2.1)를 그 문서들에 비동기 실행하는 것은 Phase 2다 — MVP는 배지 + 알림까지.

구현(2026-10-16 · 사람 결정 D1 · 4.8 백로그 E19-S01). 위 표의 칸이 실제로 일어나는 자리다. 미리보기는 영향 미리보기 API(GET …/spec-versions/{ver}/impact · 4.4 REQ-API-330)이고 CR 상세와 검토 요청 · 바로 승인 창이 같은 결과를 쓴다 — 델타와 함께 작업마다 이 승인이 하는 일(재브리핑 · 재검증 · 취소 · 중단 확인), 진행 중 클레임(세션 · 호스트), 이 문서를 참조하는 문서를 돌려준다. 제안은 사람이 고른다. ADDED의 파생 작업, MODIFIED의 완료 작업 재검증 작업, REMOVED의 미착수 작업 취소는 미리보기에 제안으로 나오고 승인하는 사람이 체크한 것만 승인과 같은 트랜잭션에서 서버가 한다(파생 · 재검증 작업은 새 승인본을 기준으로 backlog 에 만들고, 취소는 보관 사유 obsolete 로 보관한다 · REQ-API-331). 기본 체크는 파생과 재검증이고 취소는 사람이 직접 고른다 — 만드는 것은 나중에 보관하면 되지만 보관은 누군가의 계획을 지운다. 아무도 고르지 않았으면 승인할 때 그 기본값을 적용한다(2026-10-16 사람 결정 · 권장안 A) — 받은 요청 카드 · [바로 승인] 창 · nerv_spec_approve 처럼 CR 화면을 거치지 않은 승인도 파생 · 재검증 작업을 만들고 보관은 하지 않는다. 승인하는 사람은 대부분 받은 요청 카드에서 승인하는데, 고른 것만 하던 동안에는 새 요구사항의 작업이 조용히 빠졌다. 사람이 고른 것은 빈 선택("아무것도 만들지 않음")까지 그대로 존중한다 — 고른 적 없음과 빈 선택은 서버가 나눠 둔다(4.4 REQ-API-351). 중단 확인은 그 세션의 다음 하트비트가 전한다 — basis_superseded 의 그 작업 줄에 requirement_removed: true 가 붙고 세션은 그 작업을 계속할지 사람에게 묻는다. 클레임 보유 세션의 critical 알림은 cr.approved 가 바뀌거나 빠진 요구사항의 작업을 클레임한 사람에게 보낸다(§6.3). 표의 나머지 알림 칸은 이미 있는 이벤트가 맡는다 — 문서 승인(spec.approved)과 재브리핑(task.rebrief_required).

3.4 SPEC-DRIFT 역류 경로

구현하다 보면 스펙이 틀렸다는 것이 드러난다. clemvion은 이 경우를 위해 정식 경로를 만들어 5개월 운영했다: 리뷰 finding에 [SPEC-DRIFT] 태그가 붙으면 resolution-applier가 코드를 되돌리지 않고 plan/in-progress/spec-update-<area>.md 초안을 만든 뒤 ESCALATE=spec으로 격상하고, /consistency-check --spec을 거쳐 스펙에 반영한다. 요약 에이전트에는 "절대 일반 WARNING으로 뭉개지 말 것"이라는 지침이 명시돼 있다.

그림 5. SPEC-DRIFT 역류 경로. 핵심은 코드 revert가 기본값이 아니라는 것이다.

스펙이 진실이라는 원칙과 "구현에서 배운 것이 스펙으로 역류한다"는 현실을 양립시키는 유일한 방법이고, spec_drift가 Finding의 1급 태그인 이유다.

구현(2026-10-16 · 사람 결정 · 4.8 백로그 E19-S02). 위 그림이 실제로 일어나는 자리다. 보내는 길은 둘이다. 사람은 리뷰 센터의 spec_drift 발견이나 사유가 spec 인 에스컬레이션 카드에서 [CR로 보내기]를 누른다(planner · admin — 처분 권한 review:resolve 를 가진 역할 가운데 스펙을 고칠 방향을 정하는 둘이다). 에이전트는 초안을 저장하며(nerv_spec_draft_upsert) 그 발견을 finding_id 로 가리킨다. 어느 길이든 유래 스펙에 열린 CR이 있으면 그 CR에 잇고(문서마다 열린 CR은 하나다 · §3.5), 없으면 승인본의 본문으로 새 초안을 열어 CR을 만든다 — 출처는 spec_drift 다. 발견은 닫히지 않는다. 처분은 escalated(사유 spec)이고 그 CR · 근거 · 그 발견을 본 커밋을 가리킨다. planner의 카드는 CR 하나에 하나다 — "구현이 스펙을 바꿨습니다. 스펙 갱신을 승인하시겠습니까?" 와 CR 키 · 출처 발견 · 커밋을 보이고, 초안이 아직 승인본과 같으면 검토를 요청할 수 없다는 것을 보인다(같은 본문의 초안은 검토 요청이 409 cr_unchanged 다 — 고친 것이 없는데 "스펙을 고쳐 해결" 이 남지 않게). 검토 중에는 같은 CR이 스펙 결재 카드로 보이고 그 카드도 출처 발견을 보인다. CR이 승인되면 발견은 fixed 로 닫힌다 — 처분은 spec_change(스펙을 고쳐 해결)이고 근거는 승인된 그 버전이다(이 칸은 그림에 없어 이번에 정했다: 커밋이 코드 쪽 증거이듯 승인본이 문서 쪽 증거다 · §5.3). 거절되면 발견은 dismissed 로 닫히고 코드 되돌림 작업이 backlog 로 생긴다 — 제목 · 본문에 발견 · 커밋 · CR 키를 적고 담당 · 기준(기준 버전 · 요구사항)은 그 발견이 나온 작업에서 옮긴다. 작성자가 CR을 철회하면 발견은 열린 채로 남는다 — 그 CR이 길이 아니었을 뿐 지적이 사라진 것은 아니다(4.4 REQ-API-333 · 338).

3.5 CR과 문서 축의 관계

CR은 자체 수명 상태(open / in_review / approved / rejected / withdrawn)를 갖되, 승인 판정의 진실은 대상 SpecVersion의 문서 축 상태다. CR 상태는 제안 자체의 진행(철회·거절 포함)을 표현하고, 무엇이 승인된 기준인지는 언제나 SpecVersion이 답한다. 두 값 중 어느 쪽이 진실인지 미리 못 박아 두지 않으면, 값이 갈라지는 순간 판단이 불가능해지기 때문이다 — clemvion에서 plan frontmatter status와 디렉토리 위치(in-progress/ vs complete/)가 두 번 어긋난 실패(#1108·#1117)가 그 사례다.

결정 기록 — CR은 버전을 감싸고 결재는 버전이 받는다(2026-10-16 · 사람 결정 D1 · 권장안 A). 결재(티어 · 정족수 · 만료 · 바로 승인 · 일괄 승인)는 지금처럼 spec_version 이 받는다. CR 자기 결재는 만들지 않는다 — 게이트 로직을 두 벌로 만들지 않는다. 그래서 결재 대상 값 change_request 는 쓰지 않는 값으로 남는다(4.3 데이터베이스 스키마 §2.1 — enum 값을 지우는 마이그레이션은 위험만 있고 얻는 것이 없다).

  • 생성. 승인본(approved 버전)이 있는 문서에 새 초안이 생기면(초안 저장 · 되돌리기) 서버가 CR을 open 으로 연다. 승인본이 없는 첫 초안은 CR이 아니다 — 고칠 약속이 아직 없다. 문서마다 열린(열림 · 검토 중) CR은 하나이고 초안마다 CR은 하나다(§1.2 "가변 구간은 문서마다 하나"의 거울). 제목은 문서 제목, 이유는 초안의 변경 요약이고, 출처는 사람이면 human · 에이전트 세션이면 agent 다. 임포트는 CR을 열지 않는다(4.4 REQ-API-328).
  • 상태는 버전을 따라간다. 검토 요청 → in_review(위험도를 그 판정의 게이트 티어에서 채운다 — T0 · T1 low · T2 normal · T3 high · 2026-10-16 사람 확인) · 승인 → approved · 결재가 거절 · 코멘트 · 만료로 초안을 돌려보내면 → open(CR을 닫지 않는다 — 결재의 거절은 "고쳐서 다시 내라"다).
  • CR 거절은 따로 하는 행위다. planner · admin이 사람으로만 하고 사유가 필수다. 이 제안을 하지 않기로 하는 것이라 초안을 버린다(discarded — §1.2). 초안을 남기면 다음 편집이 같은 제안을 다시 열기 때문이다. 작성자(CR을 연 사람 또는 초안 작성자)가 스스로 버리면 withdrawn 이다. 둘 다 열린 CR에만 한다 — 검토 중이면 받은 요청의 카드에 대상이 사라진 결재가 남으므로 결재를 먼저 끝낸다(4.4 REQ-API-329).
  • 진실이 어긋나면 버전을 따른다. 문서 축의 전이를 거치지 않은 길(임포트 · 손으로 고친 데이터)로 초안이 이미 승인 · 대체됐으면 다음 CR을 열 때 그 CR을 버전에 맞춰 닫는다.

3.6 기준선 — 프로젝트 단위 승인 스냅샷 FR-02 확장 · 2026-08-21 MVP 포함 확정

스펙은 구현보다 앞서간다. 문서마다 draft→approved가 도는 동안, 구현은 "그때 함께 정합이던 approved 세트"를 기준으로 진행돼야 한다 — 문서 1건의 버전 핀(task.source_spec_version_id)만으로는 그 문서가 참조하는 주변 문서들의 기준이 흔들린다. 기준선은 그 세트를 이름 붙여 동결하는 1급 개념이다(엔티티 정본: 데이터 모델 §2.2, API: 4.4).

규칙내용
생성사람 전용(planner·admin) — 동결은 거버넌스 행위라 에이전트 생성 도구가 없다. 기본값은 "생성 시점의 스펙별 최신 approved 전체"이고, 항목을 큐레이션해 줄일 수 있다
구성스펙당 approved SpecVersion 1개 핀. draft·in_review는 담을 수 없다(생성 시 서버 검증)
불변생성 후 항목 집합은 바뀌지 않는다. 세트를 바꾸려면 새 기준선 — approved 스냅샷 불변과 같은 원리다
소비Task 파생 시 task.baseline_id로 맥락을 고정할 수 있고, 에이전트·웹은 nerv_spec_get(baseline=…)·?baseline= 조회로 그 세트 그대로 읽는다(2026-09-04 구현 — 4.4 REQ-API-087). 그 세트에 없는 문서는 최신으로 떨어지되 baseline_pinned:false 로 말한다. 핀 대상이 나중에 superseded 되어도 기준선 조회 결과는 변하지 않는다
기준선 작업작업에 기준선이 있으면 재브리핑 대신 기준선을 바꾼다 — 기준선과 기준 버전이 함께 옮겨 가고(출처 문서가 새 세트에 없으면 기준 버전은 그대로), 재브리핑 표시는 지워진다. 핀 문서에 새 승인본이 나와도 ready 큐에 남고 기준 드리프트를 만들지 않는다. 작업을 만들 때 출처 문서가 그 세트에 있으면 기준 버전은 그 핀이어야 한다. 구현 세션은 nerv_spec_get(task=…) 로 출처 문서의 기준 버전과 주변 문서의 핀을 함께 읽는다(2026-09-27 사람 결정 · 4.4 REQ-API-203·210)
시각 절단과의 관계특정 시각의 approved 집합은 approved_at으로 파생 가능하다(as-of manifest — 4.4). 기준선은 시각 절단이 아니라 큐레이션된 이름 있는 동결이다

기준선은 문서 축 상태 머신을 건드리지 않는다 — superseded 전이·CR 흐름은 그대로 돌고, 기준선은 그 위에 얹힌 읽기 기준일 뿐이다. 요구공학의 baseline("합의·검토·승인된 요구사항 집합의 시점 스냅샷")을 문서 1건이 아니라 프로젝트 세트에 적용한 것이며, §2.5 "승인의 유통기한"(content hash 기준 결정)과 함께 "무엇을 기준으로 만들었나"라는 질문을 어느 축에서든 답할 수 있게 한다.

4.2 ready 판정

ready(task) ⟺
      task.status == 'backlog'
  AND (task.spec_version.status == 'approved' OR task.baseline_id IS NOT NULL)
  AND 위임_명세_4요소_충족(task)
  AND ∀ d ∈ TaskDependency(task): d.status == 'done'
  AND (task.plan_approval_required ⇒ task.plan_approval.decision == 'approve')
  AND task.blocked_reason IS NULL

ready 큐는 우선순위·기한·담당 후보로 정렬된 질의 결과다. 문서가 아니다. clemvion에서 백로그 조망을 담당하던 인덱스 문서가 부패해 삭제된 뒤 "사람 머리 + audit 도구 출력"에 의존하게 된 것, 그리고 34개 in-progress plan 중 15개만 priority를 선언했던 실측이 이 설계의 근거다.

기준선으로 개발하는 작업은 핀 버전이 superseded 가 되어도 ready 다(2026-09-27 사람 결정 · 4.4 REQ-API-210). 세트가 약속이라 핀 문서의 새 승인본이 그 작업을 낡게 만들지 않는다 — 예전에는 큐에서 조용히 빠져 찾을 방법이 없었다. 기준선이 없는 작업은 그대로 재브리핑을 기다린다(§3.3).

4.3 클레임과 리스 (D-04 · FR-06)

✅
설계 결정 D-04 · 동시성 제어는 원자적 클레임 + 리스(lease)

ready 판정(의존성 그래프) → nerv_task_claim(assignee+상태 원자 전환) → TTL 리스 + 하트비트 → 만료 시 자동 회수. 클레임 시 scope(spec_ids, file_globs)를 선언하고 겹침 시 경고/차단한다. ID는 서버 발급(해시 기반)으로 파일 기반 번호 충돌을 원천 제거한다.

클레임은 "누가 이 작업을 한다"의 선언이자 "내가 어디를 건드린다"의 선언이다. 후자가 P1(세션 간 스펙 충돌)·P2(중복 작업)를 푸는 열쇠다.

4.4 scope 겹침 검사 알고리즘

# nerv_task_claim 서버측 처리 — 원자적 클레임 + scope 겹침 판정
# 입력 : task_id, session_id, scope{spec_ids[], file_globs[]}, ttl
# 출력 : {ok:true, lease_expires_at, warnings[]} | {ok:false, reason, overlaps[]}

FUNCTION claim_task(task_id, session_id, scope, ttl):
  BEGIN TRANSACTION

    # 0) 대상 행 잠금 — 중복 클레임을 DB 레벨에서 차단
    task := SELECT * FROM task WHERE id = task_id FOR UPDATE
    IF task IS NULL OR task.status != 'ready':
        ROLLBACK; RETURN {ok:false, reason:'not_ready', status:task.status}

    # 1) 비교 대상은 "살아있는" 클레임만 (만료·죽은 세션은 먼저 회수)
    reclaim_expired_leases(task.project_id)
    active := SELECT c.*, s.hostname, s.user_id
              FROM claim c JOIN agent_session s ON s.id = c.session_id
              WHERE c.project_id = task.project_id
                AND c.released_at IS NULL
                AND c.lease_expires_at > now()
                AND s.status IN ('active', 'awaiting_input')
                AND c.session_id != session_id

    # 2) 두 축(스펙·파일)으로 겹침 계산
    overlaps := []
    FOR EACH c IN active:
        # 2-a) 스펙 축 — 트리 폐포로 확장해 조상/자손 겹침까지 검출
        spec_hit := closure(scope.spec_ids) ∩ closure(c.scope.spec_ids)

        # 2-b) 파일 축 — 파일시스템을 읽지 않고 glob 패턴만으로 교차 가능성 판정
        file_hit := []
        FOR EACH g1 IN scope.file_globs:
            FOR EACH g2 IN c.scope.file_globs:
                IF globs_can_intersect(g1, g2): file_hit += (g1, g2)

        IF spec_hit ≠ ∅ OR file_hit ≠ ∅:
            overlaps += { session:c.session_id, host:c.hostname, user:c.user_id,
                          task:c.task_id, specs:spec_hit, files:file_hit,
                          severity:severity_of(spec_hit, file_hit, task, c) }

    # 3) 정책 판정 — 차단은 좁게, 경고는 넓게
    IF ∃ o ∈ overlaps WHERE o.severity == 'block':
        ROLLBACK
        emit_event('claim.conflict_blocked', task, overlaps)
        RETURN {ok:false, reason:'scope_conflict', overlaps}

    # 4) 조건부 UPDATE — 경쟁에서 진 세션은 affected_rows = 0 으로 즉시 판별
    UPDATE task
       SET status = 'claimed', assignee = session.user_id, delegate_session = session_id
     WHERE id = task_id AND status = 'ready'
    IF affected_rows == 0:
        ROLLBACK; RETURN {ok:false, reason:'lost_race'}

    INSERT INTO claim(task_id, session_id, scope, lease_expires_at = now() + ttl)
    INSERT INTO event(type='task.claimed', actor=session, is_agent=true, targets=[task])

  COMMIT

  IF overlaps ≠ ∅:
      notify(overlaps, tier='high')      # warn 은 통과시키되 양쪽 세션·담당자에게 알린다
  RETURN {ok:true, lease_expires_at, warnings:overlaps}


# glob 교차 가능성 — 두 패턴이 같은 파일을 가리킬 수 있는가 (보수적 판정)
FUNCTION globs_can_intersect(g1, g2):
    IF g1 == g2: RETURN true
    p1 := split(g1, '/');  p2 := split(g2, '/')
    i := 0
    WHILE i < len(p1) AND i < len(p2):
        a := p1[i];  b := p2[i]
        IF a == '**' OR b == '**':        RETURN true    # 이후 임의 깊이 → 교차 가능
        IF NOT segment_can_match(a, b):   RETURN false   # 리터럴 불일치 → 교차 불가
        i := i + 1
    RETURN true                                          # 접두 전부 호환 → 보수적으로 true

# 위험도 — 차단은 "같은 스펙 문서를 두 세션이 동시에 개정"하는 경우로 한정
FUNCTION severity_of(spec_hit, file_hit, t_new, c_old):
    IF spec_hit ≠ ∅ AND both_tasks_mutate_spec(t_new, c_old):  RETURN 'block'
    IF spec_hit ≠ ∅:                                           RETURN 'warn'
    IF file_hit ≠ ∅ AND same_requirement(t_new, c_old):        RETURN 'warn'
    IF file_hit ≠ ∅:                                           RETURN 'info'
    RETURN 'info'

판정 불가(예: git forge 웹훅 지연으로 커밋 범위를 모름) 시 진행을 허용하되 배너와 연속 카운터를 남기고, 임계 초과 시 "게이트가 사실상 꺼짐"으로 격상한다. 그리고 에이전트의 자기보고(STATUS 한 줄)와 실제 산출물 업로드를 분리 검증한다 — 서버에 업로드된 산출물만 진실이다.

격상은 시간 창 안의 횟수로 판정한다(2026-10-15 — 사람 결정). 프로젝트 정책의 failopen.window_hours 안에 fail-open 이 failopen.escalate_count 회 이상이면 격상한다 — admin 에게 중요 알림을 보내고 S5 세션 모니터 · S6 리뷰 센터에 배너를 표시한다. 그 창 동안 새 fail-open 이 없으면 풀린다. 격상과 해제는 이벤트로 남긴다. 위 결정의 "연속 카운터 · 임계 초과" 를 이 모양으로 읽는 이유는 정책 키 둘(4.4 API §2.1a — 기본 3회 · 24시간)이 이미 "횟수 + 시간 창" 이라 새 키가 필요 없어서다. 구현은 2026-10-15 에 들어왔다(4.8 백로그 E18-S01 · E18-S02 · 4.4 API REQ-API-318 ~ 320). fail-open 을 남긴 직후와 워커 잡이 같은 판정을 보고, 격상 상태는 표 없이 그 프로젝트의 가장 나중 격상 · 해제 이벤트(gate.failopen_escalated · gate.failopen_cleared)에서 파생한다. 격상 알림은 high 등급으로 admin 에게만 가고 해제는 알림을 만들지 않는다(§6.3). 두 키는 admin 이 S8 게이트 정책 탭에서 고친다.

커밋 범위는 작업의 최신 커밋이다(2026-10-15 — 4.8 백로그 E16-S01 · 4.4 API REQ-API-314). 조건 1~3 의 "커밋 범위" 는 그 작업에 붙은 commit 증적 가운데 서버가 가장 나중에 받은 커밋이다 — 서버는 git 의 커밋 그래프를 갖고 있지 않고 커밋 시각은 rebase 가 바꾸므로 받은 순서를 쓴다(§5.4 가 경로 타임스탬프를 버린 이유와 같다). push 웹훅의 커밋과 done 에 함께 붙인 커밋이 모두 여기 든다. done 게이트는 그 커밋을 head_sha 로 본 라운드만 센다. 리뷰 뒤에 새 커밋이 왔으면 막고 다시 리뷰받을 종류와 커밋을 알린다. 짧은 SHA 와 대소문자는 같은 커밋으로 본다. 작업에 commit 증적이 없어 커밋을 모르면 D-14 대로 신선도만 넘기고 gate.failopen 을 남긴다 — 리뷰가 없거나 열린 발견이 있으면 그대로 막는다.

fail-open 은 커밋을 모를 때만이다(2026-10-15 — 사람 결정 · 4.4 API REQ-API-314 · 321). 판정하지 못하는 경우는 둘로 나뉜다. 작업의 커밋을 모르는 것(commit 증적이 없다)은 웹훅이 오지 않은 것 같은 환경의 빈칸이라 D-14 대로 넘기고 기록한다. 리뷰가 본 것이 커밋 SHA 가 아닌 것(HEAD · 브랜치 이름)은 제출하는 쪽이 고칠 수 있는 입력이라 넘기지 않는다 — 리뷰 제출이 그런 값을 400 으로 거절하고, 그 전에 들어온 라운드는 최신 커밋을 다시 리뷰받아야 하는 것으로 막는다. D-07 이 리뷰 세션에 입력 커밋 스냅샷을 필수로 둔 이유가 여기서도 같다 — 움직이는 이름으로는 "무엇을 봤는가" 에 답할 수 없다. 처음 구현은 둘을 같은 fail-open 으로 다뤄서 head_sha: "HEAD" 로 내면 신선도를 넘을 수 있었다.

조건 5는 clemvion에서 가장 잘 작동한 규칙의 이식이다. "작업 완료가 스펙 정합 결정을 강제 동반"하게 만들면 완료 시점에 아무도 스펙을 보지 않는 사태가 구조적으로 불가능해진다. none sentinel을 허용하되 선언 자체는 필수라는 점이 핵심이다.

done 에는 사람 승인을 걸지 않는다 — 판정은 기록으로 남는다(2026-09-28 결정 · 2026-10-15 재확인, 사람 결정). done 은 위 조건을 done 게이트가 판정하고 사람은 정책(done_gate.evidence_source: ci_or_human — 에이전트가 스스로 올린 증적만으로는 닫지 못한다)과 게이트 면제 결재로 개입한다. 코드가 사람에게 가는 자리는 D-06 의 ④ PR 머지다. 사람이 승인하지 않으므로 그 판정의 감사는 task.done이 맡는다 — 적용 정책 지문, 조건마다의 결과(통과 · 면제), 면제를 썼는지를 남긴다(4.4 API REQ-API-303). 재검토 트리거와 도구 티어는 3.4 에이전트 연동 설계 §2.2가 정본이다.

clemvion에서 같은 발견이 라운드마다 새 표 행으로 재서술됐다. 한 유예 항목이 세 세션(14_01_46 / 17_15_21 / 18_19_33)에서 반복 재확인된 것이 실례이며, dedup 키가 없다는 것이 정보 모델의 최대 결손으로 지목됐다.

fingerprint 구성 요소는 3.3 데이터 모델 §5.2가 정의한다. 이 문서는 그 정의를 재정의하지 않고 인용만 한다 — 요소 목록이 두 곳에 복제되면 라운드 간 dedup이 문서마다 다르게 동작한다.

구성 요소에서 줄 번호를 뺀 이유는 코드가 위아래로 밀려도 같은 발견이어야 하기 때문이다. 같은 fingerprint가 다시 들어오면 새 Finding을 만들지 않고 기존 Finding에 occurrence를 추가한다. 그러면 이런 질의가 가능해진다 — "3라운드 이상 반복 등장했는데 아직 open인 finding", "지난 30일간 dismissed 후 재등장한 finding".

5.3 해결 추적 — 유예(wont_fix)는 1급 데이터

Finding 상태는 open → fixed / dismissed / wont_fix다. 여기에 처분 근거를 붙인다.

처분필수 부가 정보근거
fixed커밋 SHA(FK)clemvion fix(<scope>): SUMMARY#<n> 커밋 규약 + _resolution_state.json.commits_made[{sha,summary_id}]
dismissed(오탐·기각)사유 + 승인자(사람)severity 하향과 동일 취급 — 감사 대상

spec_drift 태그생성된 CR 링크§3.4 역류 경로

wont_fix는 "새 근거 없이 재상정하지 않는다"는 규칙과 함께 동작한다. 같은 fingerprint가 다시 들어와도 재상정 조건이 충족되지 않으면 리뷰어에게 "이미 유예된 항목"으로 표시되고 새 알림을 만들지 않는다 — 이것 하나로 리뷰 피로의 상당 부분이 사라진다.

5.4 게이트 판정 — 훅 1,005줄이 질의 한 줄로

clemvion의 push 게이트는 "이 브랜치의 최신 코드 변경보다 나중에 만들어진, 해소된 리뷰가 있는가"를 파일시스템 walk + 디렉토리명 타임스탬프 파싱으로 판정했다. checkout이 mtime을, rebase가 committer date를 오염시키므로 rewrite-immune 시계까지 따로 구현해야 했다.

-- "이 커밋 범위를 커버하는 해소된 리뷰가 있는가" (FR-10)
SELECT EXISTS (
  SELECT 1 FROM review_session rs
  WHERE rs.project_id = :project
    AND rs.branch     = :branch
    AND rs.head_sha   = :head          -- 신선도: 경로 타임스탬프가 아니라 커밋 동일성
    AND rs.forced_roles_satisfied      -- 커버리지: 필수 리뷰어 전원 산출물
    AND NOT EXISTS (                   -- 해소: open critical 0건
      SELECT 1 FROM finding f
      WHERE f.review_session_id = rs.id
        AND f.severity = 'critical' AND f.status = 'open')
);

커밋 SHA 연결 하나로 세 조건(커버리지·해소·신선도)이 단순 질의가 된다. 판정 불가 시의 동작은 D-14 그대로다 — 통과시키되 배너·카운터, 임계 초과 시 격상.

5.5 커버리지 계산 — P4의 답

구현 커버리지(spec) = |{r ∈ REQ(spec) : r.status ∈ (implemented, verified)}| / |REQ(spec)|
검증 커버리지(spec) = |{r ∈ REQ(spec) : r.status = verified}|                  / |REQ(spec)|
증적 결손(spec)     =  {r ∈ REQ(spec) : r.status = implemented ∧ Evidence(r) = ∅}
빈 약속(spec)       =  {r ∈ REQ(spec) : r.status = unimplemented ∧ Task(r) = ∅}

마지막 줄이 clemvion의 R-5 사례 — "spec이 plan을 가리키지 않아 어떤 plan도 책임지지 않는 빈 약속으로 영구 누락"된 텔레그램 chat-channel UI — 를 매일 자동 검출하는 질의다. clemvion은 이걸 NLP 휴리스틱(/spec-coverage, advisory·비차단)으로 근사해야 했다. 관계가 있으면 휴리스틱이 필요 없다.

구현 범위(2026-09-02 실측 기준 · 2026-10-15 관여 · 2026-10-16 워치). 위 표의 수신자를 모두 산출한다 — 채널은 아직 앱 안과 메일 요약이다(Slack 은 E17-S03).

  • approval.requested 는 지정을 본다 — assignee_user_id 가 있으면 그 사람에게만, assignee_role 이 있으면 그 역할의 멤버에게, 둘 다 없으면 역할 큐(admin·planner)로 간다. 같은 날 사람 결정으로 붙였다: 결재 경로(EP-APR)는 처음부터 지정을 보는데 알림만 보지 않아, 지정 승인자가 designer·qa 면 자기 앞으로 온 카드의 알림을 못 받았고 admin·planner 전원은 결정할 수 없는 카드의 알림을 받았다. 결정할 수 없는 카드의 알림은 §6.6 원칙 3 이 막으려는 바로 그 소음이다.
  • 관여(③)는 2026-10-15 에 들어왔다(4.8 백로그 E17-S01 · 4.4 API REQ-API-316). 표가 수신자로 적은 작성자(그 스펙 버전을 쓴 사람) · 담당자(작업 담당자) · 클레임 보유 세션 소유자 · 스레드 참여자(같은 문서 · 같은 앵커에 열린 코멘트를 쓴 사람) · 리뷰 요청자(그 발견을 관찰한 라운드를 제출한 사람)를 산출한다. 리뷰 결정 「코멘트」(spec.comment_added 의 대상이 스펙 버전)는 그 버전의 작성자에게 간다. 역할 큐(admin·planner)로 가던 이벤트는 역할 큐가 그대로 받고 관여자를 더한다 — 겹치면 한 번이다. finding.opened(critical 만) · finding.resolved 는 역할 큐 없이 관여자 — 그 발견을 관찰한 라운드의 작업(과 발견에서 만든 작업)의 담당자 · 리뷰 요청자 · 발견이 가리키는 스펙 버전의 작성자 — 에게만 간다. 지금 그 프로젝트의 멤버가 아닌 사람은 받지 않는다. 그 밖의 이벤트는 역할 큐다. 표의 "워처" 는 아래 항목이다.
  • 워치(②)는 2026-10-16 에 들어왔다(4.8 백로그 E17-S02 · 4.4 API REQ-API-342 · 343 · 사람 결정 D5 = B). 사람이 스펙 · 작업 · 영역에 워치를 건다 — 자동 등록은 없다(§2.2 결정 기록). 표가 「워처」를 적은 이벤트 가운데 알림을 만드는 넷(spec.approved · spec.rejected · spec.comment_added · task.ready)이 그 대상의 워처에게 간다. 스펙 이벤트는 그 문서의 워처와 그 문서이거나 그 조상인 영역의 워처, task.ready 는 그 작업의 워처와 기준 문서이거나 그 조상인 영역의 워처다 — 영역 워치는 그 아래 문서와 작업까지 포함한다. 관여 라우팅과 같은 자리에서 더하므로 역할 큐 · 관여자는 그대로 받고 겹치면 한 번이며, 행위자와 지금 멤버가 아닌 사람은 받지 않는다. 표의 low 줄(session.* · task.claimed · task.done)은 워처에게도 알림을 만들지 않는다(§6.2).
  • session.stale 은 그 세션을 연 사람에게만 간다(2026-10-16 · 4.4 API REQ-API-327). 예전에는 역할 큐로 가서, 행위자(멈춘 그 세션 — 행위자 이름은 세션의 주인)를 빼는 규칙이 바로 주인을 뺐다. 역할 큐는 받지 않는다 — 표의 수신자가 세션 소유자뿐이고 다른 사람의 세션은 세션 모니터(S5)와 활동 피드에서 본다. 주인이 지금 그 프로젝트의 멤버가 아니면 아무에게도 가지 않는다. 그 세션이 되살아나면 그 알림은 읽음으로 바뀐다 — 알릴 일이 끝났다(4.4 API REQ-API-352).
  • 어느 경우든 행위자 자신은 제외한다 — 자기가 한 일의 알림은 소음이다. 예외는 둘이다(2026-10-16). session.outbox_failed 는 행위자가 그 사람의 플러그인이고 알릴 사람은 자기 쓰기가 들어가지 않은 줄 모르는 그 사람이다. session.stale 은 행위자가 멈춘 그 세션이고 알릴 사람은 자기 세션이 멈춘 줄 모르는 그 세션의 주인이다.

수신자에게 실제로 닿는 경로는 notification.created 방송이다(4.4 API 명세 §3.3 — 개인 룸).

6.4 받은 요청 승격 — 알림을 줄이는 궁극의 방법

승인·질문·리뷰 요청은 알림이 아니라 작업 항목이다. 흩어진 핑 대신 미결 액션을 한 곳에서 추적하는 Agent Inbox 패턴이며, NERV의 받은 요청(S7, FR-11)이 그 화면이다. 받은 요청 항목은 자체 상태 머신 대기 → 결정 → 만료(§2.6)를 갖고, Slack·메일은 받은 요청으로 가는 딥링크만 나른다. 받은 요청에서 이미 처리된 항목은 대기 중이던 메일 다이제스트에서 빠진다(크로스 채널 dedup).

만료는 셋째 탭이다(2026-10-15 · 사람 결정 · 4.5 화면 명세 REQ-WEB-310). 받은 요청은 대기 · 처리됨 · 만료 세 탭이다. 만료 탭에는 내 큐였는데 결정 없이 만료된 카드가 만료 시각과 함께 남는다. 처리됨은 "내가 결정한 것"이라 섞지 않는다. 대기 카드는 요청 뒤 2일을 넘기면 "지연"으로 표시한다(§2.6).

6.5 배칭 · 다이제스트

인앱은 batch-on-write(이벤트가 올 때 받는 사람의 열린 묶음에 더한다), 메일은 batch-on-read(일 1회 미열람 항목 수집)로 이원화한다. 인앱 묶음은 시간 창이 아니라 읽음으로 닫는다(2026-09-27 · 아래 결정 기록).

batch key

§6.3 표의 값에 받는 사람을 더한 것. 같은 키의 열린 줄이 있으면 새 줄을 만들지 않고 그 줄의 건수를 올리며 줄을 맨 위로 올린다("스펙 3.2에 코멘트 4건"). 보통 등급만 묶는다 — critical · high 는 헤더 배지가 세는 것이라 한 건이 한 줄이다. 코드의 finding.commented(Phase 2 이벤트)는 finding:{id}:comments 다.

batch window

인앱은 창이 없다 — 사람이 읽을 때까지 열려 있고, 읽으면 닫혀 다음 알림은 새 줄로 시작한다. 수준 밖이라 읽음으로 들어온 알림(§6.1)도 같은 규칙으로 묶이되, 안 읽은 묶음과 읽음 묶음은 섞지 않는다. 메일은 켠 사람에게 그 사람의 현지 시각에 하루 한 번이다(받는 시각은 고른다 — 2026-09-28 · EM2).

조기 flush

인앱에는 없다 — 발송이 아니라 줄 하나의 갱신이라 더해질 때마다 맨 위로 온다. 메일에도 두지 않는다 — 하루 한 통이고, 줄이 20개를 넘으면 그 한 통이 20줄까지 적고 나머지를 "그 밖에 N건" 으로 줄인다(2026-09-28 · EM4).

idempotency

한 이벤트는 한 사람에게 한 줄 또는 한 묶음에만 든다(notification(event_id, user_id) · notification_batch_event(event_id, user_id) 유일). 동시 이벤트가 두 묶음을 여는 경쟁은 "열린 묶음은 키마다 하나" 유일 인덱스가 막는다(4.3 데이터베이스 REQ-DB-029·030).

결정 기록(2026-09-27 · 사람 결정 G1~G4 · 다이제스트 검토). 명세는 보통 등급을 5분 창으로 묶는다고 적었지만 묶는 작업이 없어 알림이 한 건씩 쌓였다. 로컬 실측(참조 스펙 재검토 알림 1,590행)에서 대상 × 5분 창은 582줄, 승인 한 건 단위는 150줄, 대상을 읽을 때까지 한 줄은 36줄이었다 — 같은 문서가 여러 번 승인되는 흐름에서는 시간 창이 거의 줄이지 못한다. G1: 앱 안 묶음만 MVP 로 들인다(4.1 MVP 범위 FR-12). G2: 같은 대상을 읽을 때까지 한 줄로 묶는다(GitHub 스레드 알림의 모양). G3: 보통 등급만 묶는다. G4: 메일 다이제스트는 앱 안 묶음이 자리 잡은 뒤 따로 정한다.

결정 기록(2026-09-28 · 사람 결정 EM1~EM9 · 알림 메일 요약). G4 로 미뤄 둔 메일을 정한다. 알림은 앱 안에만 있어 앱을 자주 열지 않는 사람에게 알릴 길이 없었고, 메일을 보내는 배관(발송 큐 · 워커 · 재시도)은 이미 있었다. EM1: Phase 2 를 앞당겨 착수한다(4.1 MVP 범위 착수 기록 — MVP 범위 표는 그대로). EM2: 하루 한 번, 받는 사람의 현지 시각(기본 09:00). EM3: 기본은 꺼짐 — 켠 사람에게만. EM4: 결정 대기 수 + 중요 + 보통 묶음을 담되 안 읽은 것 가운데 지난 요약 뒤에 새로 생기거나 건수가 늘어난 줄만 — 읽음 상태가 이미 채널을 넘는 중복을 걸러 준다(§6.4 · §6.6-4). EM5: 시간대와 언어는 켤 때 브라우저의 값을 저장하고 설정에서 고친다. EM6: 사람당 한 통, 조직 → 프로젝트로 나눈다. EM7: 키 · 제목 · 건수 · 이름까지, 본문은 없다. EM8: 설정 링크와 로그인 없이 한 번에 끄는 링크(RFC 8058). EM9: 보낸 메일은 7일 뒤 발송 큐에서 지운다. 결정 이름은 §7 게이트 번호(G1~G5)와 겹치지 않게 EM 을 쓴다.

6.6 피로 방지 원칙 다섯

  1. 가치 위계를 먼저 정한다. 티어가 채널과 배칭 규칙을 결정하지, 그 반대가 아니다.
  2. 선호 센터를 1차 출시 범위에 넣는다. 카테고리 × 채널 × 빈도 × 방해금지 시간. 선호 센터를 둔 제품은 발송량을 줄이지 않고도 수신거부가 최대 30% 감소한다는 실측이 있다. (2026-09-27 — 채널이 인앱 하나인 동안 프로젝트별 수준 한 축으로 시작했다 · §6.1 · 사람 결정 N3)
  3. 결정이 필요한 것만 받은 요청으로. 나머지는 피드다. 받은 요청 배지 숫자는 "내 결정을 기다리는 것"만 센다.
  4. 중복은 채널을 넘어 제거한다. 받은 요청에서 처리된 항목은 예약된 다이제스트·Slack 발송에서 취소한다.
  5. 에이전트 진행 상황은 알림이 아니라 화면이다. 실시간이 필요한 것은 WebSocket으로 밀고(NFR-02), 사람의 개입이 필요할 때만 받은 요청 항목이 생긴다.

clemvion에도 BYPASS_DEFAULT_BRANCH_GUARD=1 같은 환경변수 탈출구가 있었지만 사용 사실이 어디에도 남지 않았다. NERV의 BYPASS는 Approval 엔티티(대상: 게이트 면제)로 만들어지고, 사유·범위·유효 시간을 받으며, admin 알림과 감사 로그에 남는다. 같은 경로에서 면제가 반복되면 그것은 게이트 설계가 틀렸다는 신호이며 정책 조정 대상이 된다 — clemvion이 실패 이력에서 게이트를 사후에 키워 온 방식을 데이터로 앞당기는 장치다.

범위는 리뷰 종류다(2026-10-09 — clemvion 보고 · 4.4 API REQ-API-274). 완료 조건이 code · consistency 리뷰를 요구하는 프로젝트에서 코드를 내지 않은 작업(승인된 스펙 14편의 일관성 재검토 · 스펙 초안만 쓴 작업)은 code 라운드를 받을 길이 없었다. 면제는 리뷰 커버리지를 통째로 넘기는 것밖에 없었고, 그 면제를 낼 화면도 없었다 — 남은 길은 변경 없이 code 리뷰를 꾸며 내는 것이었고, 그러면 하지 않은 리뷰가 기록에 남는다. 면제가 종류(kinds)를 받는다. done 게이트는 그 종류만 요구에서 빼고 나머지는 그대로 본다. 누가 면제할 수 있는지는 §1.6 표 그대로다 — 코드 계열(code·merge)은 developer · admin, 스펙 계열(consistency·spec_coverage)은 planner · admin. 코드를 낸 작업의 코드 리뷰는 면제되지 않는다 — 커밋 · PR · 코드 경로 증적이 붙은 작업에서는 그 면제를 받지 않고, 면제 뒤에 붙으면 done 게이트가 그 면제를 세지 않는다. 증적만으로 "코드 없음"을 추정해 자동으로 빼는 안은 택하지 않았다 — 코드를 내고 증적을 빼면 게이트를 피할 수 있고, 그 판단은 사람이 기록으로 지는 편이 맞다. done이 아닌 종료 상태(closed)도 두지 않았다 — 이 작업들은 할 일을 끝냈고, 구현 축은 done을 끝난 것으로 센다.

범위를 고르지 않은 면제는 admin의 것이다(2026-10-11 — 사람 결정 · 4.4 API REQ-API-293). 2026-10-09에 남겨 둔 일이다. 범위 없는 면제는 admin · planner · developer 누구나 낼 수 있어서 planner가 code 리뷰를, developer가 스펙 리뷰를 통째로 넘길 수 있었다 — §1.6 표(admin ●)와 어긋났다. 이제 admin만 범위 없는 면제로 리뷰 커버리지 전부를 넘긴다. planner · developer가 종류 없이 면제하면 그 역할이 면제할 수 있는 종류 전부로 풀어 읽는다(planner는 consistency · spec_coverage, developer는 code · merge). 기록(bypass_kinds · gate.bypassed)에는 풀어 읽은 종류와 그렇게 읽었다는 표시(expanded)를 남긴다 — 감사가 "무엇을 넘겼나"에 바로 답한다. 종류로 나뉘지 않은 조건(정책이 true인 리뷰 커버리지)과 작업이 아닌 대상의 면제는 그래서 admin만 낸다. 고른 안 밖의 둘도 적어 둔다: 범위 없는 면제를 admin 전용으로 막기만 하는 안은 표와 정확히 맞지만 지금 쓰는 요청이 403이 된다. 표를 실물에 맞추는 안은 2026-10-09에 종류를 나눈 뜻을 약하게 한다.
