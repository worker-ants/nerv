화면 명세

MVP 웹앱(Vite + React SPA)의 화면을 구현 착수 가능한 수준으로 확정한다 — 라우팅 맵과 앱 셸, 화면별 데이터 소스·WebSocket 무효화·컴포넌트·폼 검증·EARS 수용 기준(REQ-WEB-*), TipTap 에디터의 노드 화이트리스트와 md 왕복 규칙, 초안 편집 리스 UX, 그리고 제안서 팔레트의 Tailwind 토큰 이식. MVP 라우트는 전부 와이어프레임을 갖는다 — S1~S8의 정본은 3.6 화면 설계이고, 그 문서에 없는 MVP 신설 화면(앱 셸·로그인·온보딩·알림 센터)과 하위 뷰(스펙 목록·작업 상세 패널)의 그림은 이 문서가 소유한다(§1.6 커버리지 표).

프로젝트를 고를 길이 화면에 없었다(2026-08-24 — 사람 지적). 사이드바는 현재 프로젝트의 이름만 적어 두었고, 옮겨 가는 경로는 퀵 스위처(⌘K)뿐이었다 — 단축키를 아는 사람만 쓸 수 있는 길은 길이 아니다. 조직 select 오른쪽에 프로젝트 select 를, 그 오른쪽에 그 프로젝트로 가는 링크를 둔다(2026-08-30 정정 — 당시에는 이 자리를 "헤더 홈 오른쪽"이라고 적었다). 헤더 링크는 개요일 때만 활성이다.

헤더의 홈 링크를 걷는다(2026-08-30 — 사람 지시). 로고가 이미 / 로 간다 — 같은 목적지로 가는 길을 둘 두면 헤더에서 가장 비싼 왼쪽 끝을 한 곳이 두 번 차지한다. 로고를 누르면 홈이라는 것은 웹의 기본 약속이라 배울 것이 없고, 걷어낸 폭은 프로젝트 이름처럼 읽어야 아는 것이 갖는다. 로고에는 title 로 목적지를 적어 둔다 — 보이는 글자는 브랜드(NERV)로 남긴다.

셸의 조형은 시안을 따르되 IA 는 위 그림이 정본이다(2026-08-23). 시안은 헤더를 브레드크럼으로 두고 받은 요청을 프로젝트 사이드바로 내렸는데 그대로 받지 않는다: 받은 요청·알림은 조직 전역이지 프로젝트 소속이 아니라 프로젝트가 여럿일 때 자리가 틀린다.

  • 로고는 글리프(⬢)가 아니라 채운 사각형 마크다 — 글리프는 주변 글자와 같은 무게라 정박점이 되지 못한다.
  • 프로젝트에도 색 배지를 준다 — 이름만 있으면 어느 프로젝트인지 읽어야 안다.
  • 사이드바 nav 는 29px 줄이고 세션 은 활성 건수 배지를 단다(EP-PRJ-03 이 이미 주는 값이다).
  • 사이드바 바탕은 본문보다 아주 조금만 가라앉는다 — 패널이 아니라 여백에 가깝다.

브랜드 표기를 테스트가 문자로 못 박지 않는다 — 셸 테스트가 지키는 것은 "가입 뒤 셸에 착지한다"이지 로고 글자가 아니다.

1.3a 전역 퀵 스위처 — ⌘K (QuickSwitcher)

전역 헤더의 "🔍 전역 검색"의 실체이자 대규모 프로젝트의 기본 이동 수단이다. 트리 스크롤 대신 타이핑 → Enter로 어디서든 어디로든 간다.

1.4 실시간 계약 — 구독 룸과 쿼리 무효화

  1. 룸 2종 — user:{id}는 연결 성공 시 서버가 자동 join, project:{id}는 프로젝트 화면 진입 시 클라이언트가 join emit(서버가 멤버십 검사, 이탈 시 leave — api.md §3.2).

1.7 언어 전환 (2026-08-23 신설)

화면 문구의 정본은 @nerv/schema 카탈로그다(4.2 §3.4). 화면이 정하는 것은 어떤 언어로 보이나와 어디서 바꾸나 둘뿐이다.

  • 고르는 순서: 사용자가 고른 값(localStorage) → navigator.languages → 기본값 ko. 고른 값이 브라우저 언어를 이긴다 — 브라우저 설정이 바뀌었다고 화면 언어가 저 혼자 바뀌면, 고른 적 있다는 사실이 배신당한다.
  • 바꾸는 자리: 사용자 메뉴(§1.3 [지민 ▾]) 안. 자주 바꾸는 것이 아니고 계정에 붙은 설정이라 헤더에 자리를 내주지 않는다. 언어 이름은 그 언어로 적는다(한국어 · English) — 읽을 수 없는 말로 적힌 선택지는 고를 수 없다.
  • 서버에도 같은 언어를 알린다: 모든 API 호출에 Accept-Language 를 싣는다(4.4 §1.4). 버튼은 영어인데 에러 토스트만 한국어인 상태가 절반만 된 i18n 이다.
  • <html lang> 을 맞춘다: 스크린리더의 발음과 브라우저의 줄바꿈 규칙이 이 속성을 읽는다.

1.7a 테마 (2026-08-28 신설 — 사람 요청)

언어와 같은 규칙, 다른 소유자다. 고른 값은 이 브라우저에 기억하고 고르지 않았으면 환경(prefers-color-scheme)을 따르는 것은 §1.7과 같다. 다른 것은 어디에 붙는가다 — 언어는 계정에 붙는 성질이지만 테마는 기계에 붙는다: 같은 사람이 낮의 노트북에서는 밝게, 밤의 데스크톱에서는 어둡게 쓴다. 그래서 서버로 보내지 않는다.

  • 고르는 것은 셋: 밝게 · 어둡게 · 시스템. 시스템은 "고르지 않겠다"는 선택이고, 그것을 고른 사람의 화면은 시스템이 바뀌면 따라 바뀐다 — 그게 그 선택의 내용이다.
  • 바꾸는 자리: 사용자 메뉴의 언어 바로 아래(§1.3). 둘 다 "이 화면을 어떻게 볼 것인가"이고, 같은 자리에 같은 모양으로 있어야 한 번 찾은 사람이 다시 찾는다.
  • CSS 는 system 을 모른다: 스크립트가 풀린 값(light|dark)만 <html data-theme> 에 적고, 팔레트는 [data-theme='dark'] 한 곳에만 둔다. 미디어 쿼리에도 팔레트 한 벌을 더 두면 두 벌이 되고, 두 벌이 되면 언젠가 한쪽만 고친다 — 4.2의 토큰 파일은 그 사고를 이미 한 번 겪었다(다크가 @theme 안에 있어 라이트 팔레트가 죽은 코드였다). 미디어 쿼리에는 스크립트가 붙기 전 한 프레임을 위한 배경색 두 줄만 남긴다.
  • color-scheme 도 함께 적는다: 스크롤바·기본 폼 컨트롤처럼 브라우저가 직접 그리는 것들은 CSS 변수를 모르고 이 속성만 본다.
  • Provider 를 두지 않는다(구현 메모): 테마의 실체는 문서 속성과 localStorage 이지 React 상태가 아니다. context 로 감싸면 셸을 그리는 테스트마다 래퍼를 하나씩 더 기억해야 하고(실측: 스펙 11개가 한꺼번에 깨졌다) 그렇게 늘어난 래퍼는 언젠가 빠뜨려진다.

1.8 권한과 권한 판정 (2026-08-24 신설 — 사람 보고)

화면은 권한을 정하지 않는다. 정본은 서버다(4.4 API 명세 §1.6a). 화면이 하는 일은 서버가 무엇을 허용할지 미리 말해 주는 것뿐이고, 그래서 두 판정은 같은 규칙이어야 한다 — 갈라지면 사람은 화면을 믿는다.

점화 기록(2026-08-24). admin 계정으로 스펙 메타 편집이 "planner·admin 만 가능합니다"로 잠겨 있다는 보고. 원인은 화면이 멤버십 한 행만 보고 역할을 판정한 것이었다 — 조직 단위로만 소속된 admin 은 project_slug === null 행 하나를 갖는데, 프로젝트 슬러그로 찾으면 걸리지 않아 "아무 역할 없음"이 된다. 서버는 이미 합집합으로 판정하고 있었으므로 화면이 서버가 허용할 일을 못 한다고 말하고 있었다. 같은 뿌리에서 네 화면이 함께 틀려 있었다(메타 편집 · 게이트 정책 · 토큰 발급 · 리뷰 처분).

부르는 자리와 관리하는 자리가 같아야 한다. 멤버 표는 이미 있는 사람의 역할만 켜고 껐고, 새 사람을 넣는 입력칸이 화면에 아예 없었다 — 서버의 EP-MBR-02 는 기존 사용자만 찾으므로 신규 사용자는 어느 쪽으로도 들어올 수 없었다. 규약의 정본은 4.4 API 명세 §2.1b.

2.4b 트리 조작 (2026-08-23 정정)

트리의 깊이는 원래 제한이 없었다 — API(EP-SPEC-01)는 전 계층을 한 응답으로 주고 clemvion 실측은 4단계다(11 / 95 / 31 / 4). 2단계로 보이던 것은 렌더링 선택이었고, 그 선택에 결함이 하나 있었다.

전부 펼치는 비용을 걱정할 자리가 아니다. EP-SPEC-01은 원래 전 계층을 한 응답으로 준다(§2.4b 머리) — 깊이 1 기본이 아낀 것은 요청이 아니라 DOM 줄 수뿐이고, 규모의 부담은 가상 스크롤이 지기로 이미 정해져 있다(REQ-WEB-044). 그래서 REQ-WEB-044의 "폴더 단위 지연 로드"는 처음부터 구현된 적이 없는 서술이었고, 여기서 그 문구를 걷는다(아래 표에서 정정).

수는 둘이다 — 표시 N / 전체 M. 총계만 적으면 트리는 141을 약속하고 106만 지킨다. 사이드바는 부분이므로 부분임을 스스로 말하고(106 / 141), 전수 목록은 늘 표시 141 / 전체 141이라 그 수가 계약의 증거가 된다. 표 탭도 같은 표기를 쓴다 — 두 탭의 수가 다르다는 것을 사람이 발견하는 자리가 화면 안이어야 한다.

수를 두는 자리는 시안(§2.4 (3))의 목록 발치가 아니라 조작 줄이다: 141줄짜리 목록의 발치는 화면 밖이고, 수를 바꾸는 것([전체 접기]·트리 필터)이 그 줄에 있어 누르는 자리에서 수가 줄어드는 것이 보인다.

가상 렌더도 같은 줄을 그린다. 전수가 기본이 되면 200편을 넘긴 프로젝트는 첫 화면부터 가상 스크롤 분기로 들어가는데, 그 분기는 삼각형도 자식 수도 그리지 않아 접을 수단이 통째로 사라졌다. 두 분기가 같은 줄 컴포넌트를 쓰게 했다.

"전부 있다"고 말하려면 경계도 말해야 한다. 보관은 그 경계다.

§2.4는 처음부터 두 가지를 적어 두었다 — 목록의 [보관 보기] 토글(?include_archived=true)과 단건 진입 시 상단 배너 + [복원]. 둘 다 구현되지 않았다. 실측(2026-08-29 · sudoku 잎 하나를 보관해 확인): 표는 6→5행으로 줄고, 토글은 화면에 없고(0개), 상세 페이지는 평소와 똑같이 열렸다 — 보관됐다는 말도, 되살릴 버튼도 없었다. 메타 다이얼로그로 보관은 할 수 있으니, 웹만 쓰는 사람에게 보관은 되돌릴 수 없는 일이었다.

같은 결함을 프로젝트 쪽에서 이미 한 번 고쳤다(4.4 §2.1 — 보관한 프로젝트가 모든 경로에서 409 라 복구조차 못 하던 일). 스펙에도 같은 규약을 세운다.

트리·표가 보관을 가르려면 응답이 그것을 말해야 한다 — EP-SPEC-01·19 노드에 archived_at 을 싣는다(4.4 §2.2).

그리고 그 규칙이 한쪽에만 있었다. 복원은 부모가 보관됐으면 막았는데(parent_archived) 생성·이동에는 같은 검사가 없었다 — 보관된 부모를 지정해 스펙을 만들면 201 이었고(실측 2026-08-29), 그 문서는 기본 트리에서 부모를 못 찾아 화면에서 사라졌다. 만든 사람도 다시 찾지 못한다. 서버가 세 경로에 같은 규칙을 쓴다(4.4 §2.2 · REQ-API-039).

화면에도 방어를 남긴다. renderLevel 은 뿌리에서 내려가므로 부모를 못 찾은 노드는 조용히 빠진다 — 서버가 그 경로를 막은 뒤에도, 화면은 자기가 받은 목록을 다 그려야 한다(REQ-WEB-106). 부모를 못 찾으면 뿌리 층에 그린다. 이 결함을 지키고 있던 단위 테스트가 하나 있었다("부모가 목록에 없어도 잃어버리지 않는다" — 맵에 남아 있는 것을 잃지 않은 것으로 읽었지만, 화면에는 나오지 않았다).

2.4a 관계 그래프 (2026-08-23 신설)

스펙 목록(/p/:proj/specs)에 트리 / 표 / 관계 그래프 세 탭을 둔다(표는 §2.4c). 별도 라우트로 가르지 않는 이유는 둘이 같은 질문의 두 답이기 때문이다 — 계층으로 찾을 때와 관계로 찾을 때. 라우트를 나누면 둘을 오가며 비교할 수 없다.

데이터는 EP-SPEC-19 GET …/specs/graph 가 노드 + 간선을 한 응답으로 준다. 트리와 관계를 두 번에 나눠 받으면 그 사이의 변화가 끝점 없는 간선으로 화면에 남는다 — 그래프는 한 시점의 스냅샷이어야 읽을 수 있다.

밀도가 이 화면의 유일한 설계 문제다. clemvion 실측은 노드 141 · 간선 1,253이고 최다 피참조 문서는 52개의 선을 받는다. 힘기반 배치에 그대로 넣으면 털뭉치가 되고, 털뭉치는 "이 문서를 고치면 무엇이 흔들리나"에 답하지 못한다. 그래서 셋을 쓴다.

  1. 영역으로 묶는다 — 트리의 부모(area)를 compound 노드로 만들어 계층과 참조를 한 좌표계에 그린다. 선이 영역 안/밖으로 갈리면서 구조가 드러난다.
  2. 중심 모드 — 한 문서에서 1~2 hop만. 방향을 가리지 않는다: 영향 범위에는 내가 참조하는 것과 나를 참조하는 것이 둘 다 들어가고, 나가는 선만 따라가면 역참조라는 가장 중요한 절반이 빠진다.
  3. 차수 기반 크기 — 허브가 커서 먼저 눈에 들어오게. 색은 spec.type에 §4.2 상태 토큰을 그대로 배정한다(그래프만 다른 색 체계를 갖지 않는다).

렌더링은 Cytoscape.js + fcose다(2026-08-23 — 스택 추가, 4.1 §2.1). 라이브러리를 들인 이유는 compound 레이아웃이다: 영역 묶음을 자체 구현하면 그것이 곧 레이아웃 엔진을 쓰는 일이 된다. gzip 172KB라 탭을 누를 때 지연 로드한다 — 대부분의 방문은 트리만 쓰고, 그 비용을 목록 화면 전체가 미리 치를 이유가 없다(실측: 목록 청크 552KB → 5KB).

그래프는 읽기 전용이다 — 여기서 문서를 재배치하는 경로(부모 변경·정렬)는 두지 않는다. 트리가 그 자리다. 노드를 끌어 그림 위의 자리를 바꾸는 것은 이 규칙에 걸리지 않는다(2026-08-27 개정 — 아래 "밀집한 자리는 사람이 푼다"). 데이터를 쓰지 않는다는 뜻에서 읽기 전용이다.

노드를 누르는 것은 "연다"가 아니라 "고른다"이다 (2026-08-24 개정 — 사람 지시)

예전에는 탭 한 번이 곧 문서 이동이었다. 그래서 그래프에서 무엇 하나를 자세히 보려면 화면을 떠나야 했고, 돌아오면 배치가 다시 계산돼 방금 보던 그림이 사라졌다 — 탐색 도구가 탐색을 끊었다.

  • 고르면 강조한다: 고른 노드와 그 이웃·간선만 남기고 나머지는 가라앉힌다(opacity 0.12). 지우지 않는 이유는 지도가 지도로 남아야 하기 때문이다 — 주변이 사라지면 어디를 보고 있는지 알 수 없다. 영역 상자는 덜 가라앉힌다(0.4): 노드와 같이 지우면 고른 문서가 어느 영역에 있는지를 잃고, 그대로 두면 전부 흐려진 화면에서 상자만 남아 지도가 뒤집힌다.
  • 오른쪽 패널이 열린다: 머리에 고른 문서의 이름과 키, 그 아래 전체 · 역참조 · 레퍼런스 탭과 건수, 그 아래 이웃 목록. 관계 종류(references·refines…)를 줄마다 적는다. 탭·라벨·건수 표기·전체 탭의 구분선까지 레일(§2.4)과 같은 컴포넌트(RelationTabs)를 쓴다 — 각자 그리면 조금씩 갈라지고, 그때 사람은 그 둘이 같은 것인지부터 의심한다.
  • 다른 문서를 고르면 탭도 처음으로 돌아간다. 역참조가 없는 문서를 골랐는데 역참조 탭이 남아 있으면 빈 패널이 열리고, 사람은 그것을 "관계가 없다"로 읽는다.
  • 이동은 패널의 이름을 누를 때만 일어난다. 머리의 이름은 고른 문서로, 목록의 이름은 그 이웃으로 간다.
  • 패널이 세는 것은 화면이 아니라 데이터다: 중심 모드 1 hop에서 이웃의 이웃은 그려지지 않지만 패널은 실제 관계 전부를 적는다. 화면을 따라 줄이면 패널이 "이 문서는 이것뿐"이라고 거짓을 말한다.
  • 놓는 길은 셋이다 — 바탕 누르기 · 패널의 ✕ · Esc.
  • 패널이 열리면 캔버스가 288px 좁아진다. 고른 노드가 시야 밖으로 밀려났을 때만 시야를 옮기고 줌은 건드리지 않는다 — 누를 때마다 화면이 튀면 훑는 일 자체가 어지러워진다.

영역 상자는 노드가 아니라 배경이다 (2026-08-27 개정 — 사람 보고)

영역 안에서 끌면 화면이 움직이지 않았다. cytoscape는 노드 위에서 시작한 드래그를 "그 노드를 잡는 일"로 보는데, 이 그래프는 읽기 전용이라 아무 노드도 잡히지 않는다(autoungrabify) — 그래서 상자 안에서 끌면 아무 일도 일어나지 않고, 손을 뗄 때 그 영역만 골라졌다. 영역으로 묶으면 상자가 화면의 대부분을 덮으므로(clemvion 실측: 영역 16개) 끌 수 있는 바탕은 상자 사이의 틈뿐이고, 그때 사람은 "이 그래프는 안 움직인다"고 읽는다.

영역 상자는 배경이다. 그 위에서 시작한 드래그는 화면 이동으로 넘기고(cytoscape panify()), 누르기 한 번은 그대로 그 영역 문서를 고른다 — 끄는 것과 누르는 것은 다른 동작이다.

머리 아래 남는 세로는 캔버스가 갖는다 (2026-08-27 개정 — 사람 지시)

목록의 트리 / 표 / 관계 그래프 탭은 검색 줄 아래, 화면 머리 안에 선다. 탭이 따로 한 줄을 차지하면 제목 오른쪽의 빈자리는 그대로 둔 채 본문만 밀려 내려간다 — 화면에서 가장 비싼 것은 세로다.

캔버스 높이도 70vh로 못 박지 않는다. 머리 아래 남는 세로를 전부 가져가고(선택 패널은 캔버스와 같은 높이로 늘어난다), 좁은 창에서는 최소 높이가 그림을 지킨다. 밀도가 이 화면의 유일한 설계 문제이므로 캔버스 100px은 곧 읽을 수 있는 노드 수다(실측 1440×900: 캔버스 611px → 650px, 본문 시작 32px 위로).

그리고 그 높이는 확정이다(2026-08-27 개정 — 사람 보고). 높이를 "최소 이만큼"으로만 잡으면 패널이 길어질 때 화면이 따라 늘어난다: 이웃 93개짜리 문서(clemvion data-model)를 고르면 패널이 4,771px, 캔버스도 같은 높이, 문서 전체가 5,016px가 됐다 — 관계를 보려고 연 패널이 그 관계를 그린 지도를 화면 밖으로 밀어냈다. 그래프를 보는 동안 화면 높이는 확정되고, 넘치는 것은 패널 안에서 스크롤한다(좌측 트리 레일과 같은 규약 — 화면에 고정된 상자가 자기 내용을 흘린다).

트리·표는 반대다. 문서가 스크롤한다 — 141줄짜리 목록을 화면 높이에 가두면 스크롤이 두 겹이 되고, 안쪽 스크롤은 바깥 스크롤에 가려 있다는 것 자체가 잘 보이지 않는다.

머리는 한 줄, 조종기는 캔버스 위 (2026-08-27 재검토 — 사람 지시)

높이를 확정한 뒤에도 화면이 쓰는 856px 중 201px(23.5%)가 캔버스가 아니었다(실측 1440×900). 그중 제목·검색 줄(32px)을 뺀 나머지는 배치 때문에 생긴 것이다.

걷어낸 것얼마왜 그 자리가 아니었나
탭 줄39px검색 아래에 둔 앞의 배치(v0.32)는 세로 한 줄은 아꼈지만, 보기 방식을 바꾸는 물건이 검색과 한 덩어리로 묶여 화면 오른쪽 끝에 앉았다. "스펙을 무엇으로 보는가"는 제목 바로 다음 질문이라 제목을 따라다녀야 한다
조종기 줄35px모드·hop·영역 묶기·[다시 배치]·건수는 전부 캔버스에만 작용한다. 페이지 행으로 두면 영구히 세로를 먹고, 트리·표 탭에서는 아무 일도 안 하면서 자리만 지킨다
안내 줄23px네 가지 제스처는 처음 한 번 필요하고 그다음부터는 소음이다. 같은 문장이 매뉴얼 스펙 장에 이미 있다

머리는 제목 · 탭 · 검색 한 줄로 끝난다. 조종기는 캔버스 왼쪽 위에 반투명 칩으로 얹고(칩에만 포인터 이벤트를 주어 캔버스의 제스처를 삼키지 않는다), 건수는 지도의 축척 표기처럼 오른쪽 아래 모서리로 내린다. 안내는 칩 끝의 물음표 뒤에 접고 매뉴얼로 가는 링크를 단다 — 사라지는 것이 아니라 접히는 것이다.

공통 여백(py-6·mb-6)과 27px 제목은 건드리지 않았다(§4 · v0.19). 이 화면만 리듬을 깨면 열세 화면이 갈라지고, 탭마다 머리 높이가 달라지는 것도 눈에 걸린다.

실측 1440×900: 캔버스 655px → 752px(+15%), 화면의 88%가 그래프다. 트리·표도 같은 한 줄 머리를 쓰므로 34px 위로 올라온다.

밀집한 자리는 사람이 푼다 (2026-08-27 개정 — 사람 지시)

배치는 힘기반 계산의 한 번의 답일 뿐이라, 밀집한 자리에서는 이름이 서로를 가린다. 그 자리를 푸는 손잡이를 셋 준다.

  1. 노드를 끌어 옮긴다. 바뀌는 것은 그림 위의 자리뿐이고 부모도 정렬 키도 서버로 가지 않는다. 영역 상자는 여전히 배경이라 그 위를 끌면 화면이 움직인다(panify() 가 잡기를 끈다) — 끄는 것과 옮기는 것이 한 화면에서 갈린다.
  2. [다시 배치] — 배치를 다시 계산한다. randomize 라 누를 때마다 다른 답이 나오는 것이 이 버튼의 쓸모다: 엉킨 자리는 한 번 더 굴리면 풀리고, 손으로 흐트러뜨린 뒤 되돌리는 길도 이것 하나다. 고른 문서·중심 모드·패널은 그대로 남는다(그림만 다시 그린다).
  3. 읽을 수 없는 라벨은 그리지 않는다. 전체 보기의 기본 배율은 0.42 라 9px 라벨이 화면에는 3.8px로 찍힌다(실측 2026-08-27 · 노드 125개). 그건 글자가 아니라 얼룩이고, 얼룩 125개가 그림을 덮으면 정작 보려던 구조가 안 보인다. 배율이 올라가 8px이 되는 순간부터 이름이 나타난다. 영역 이름은 예외다 — 열여섯 개뿐이고 지도의 지명이라, 이것까지 지우면 어디를 보고 있는지 알 수 없다.

손으로 옮긴 자리는 그래프를 다시 그릴 때(중심 모드·hop·영역 묶기 토글) 사라진다. 배치를 서버에 저장하지 않기 때문이고, 저장하면 그것은 사람마다 다른 그림이 되어 "같은 것을 보고 이야기한다"는 그래프의 쓸모를 깎는다.

  • 스펙 키가 바뀌면 그 화면의 상태를 전부 비운다.
  • 편집기에는 문서별 key 를 준다. 본문 갱신을 고치는 것은 상태 비우기지만(실측으로 갈라 확인), key 가 막는 것은 되돌리기 이력이다 — 문서 B 에서 ⌘Z 가 문서 A 의 글을 되살리면 안 된다.
  • 이 결함은 E2E 여야 잡힌다. jsdom 단위 테스트로 먼저 써 봤더니 수정을 빼도 통과했다 — 잡지 못하는 테스트는 없는 것보다 나쁘다.

칸반 레인: blocked / ready / claimed / in_progress / in_review / done(7d) — 전부 가로줄이다. backlog는 필터로 노출.

blocked 를 하단 접이식에서 가로줄 맨 앞으로 옮겼다(2026-08-23 — 사람 판단). 하단에 두면 보드를 다 지나 스크롤해야 닿고, 흐름 끝에 두면 여섯 번째 칸이라 1440px 화면에서도 잘린다 — 둘 다 "있긴 한데 안 보인다"이다. 막힌 일은 각주가 아니라 먼저 풀어야 할 것이라 흐름 앞에 세운다. 레인 바탕도 위험색 계열로 옅게 깔아 같은 가로줄에 있어도 성질이 다름을 보인다.

패널은 가로로만 배치한다(2026-08-23). 세로로 쌓인 패널은 스크롤 없이 안 보이고, 그 순간 "지금 무엇이 흐르고 있나"라는 이 화면의 물음에 답하지 못한다.

폭이 좁은 자리에 놓이는 목록은 컨테이너 폭을 본다. 뷰포트 미디어 쿼리는 여기서 거짓말을 한다 — 화면은 1440px 인데 세션 줄이 놓인 칸은 350px 일 수 있고(대시보드), 그때 고정 폭 열이 넘쳐 가운데 칸이 한 글자 폭으로 찌그러진다(실측 2026-08-23). @container 로 자기 폭을 보고 좁으면 작업 줄과 사유가 제 줄로 내려간다.

긴 레일은 스스로 스크롤한다. sticky 로 붙여만 두면 내용이 화면보다 길 때 아래쪽이 영영 닿지 않는다 — 역참조 18건이면 이미 그렇다.

  • 이미지가 왕복에서 사라지고 있었다(REQ-WEB-126). 편집기에 image 노드가 없어 ![…](…) 이 버려졌고, 사람이 문서를 열어 한 글자만 고치면 모든 이미지가 삭제됐다(저장은 성공하면서). 테스트가 없어 아무도 못 봤다.
  • 세션 레일이 "Bash / Bash" 를 383번 반복했다(2026-09-01 — 사람 보고 · REQ-WEB-123·124). 화면 잘못이 아니라 적재가 그것만 남겼다. 원문 보관으로 정책을 바꾸고(4.4 REQ-API-065) 화면은 셋을 한다 — 묶고 · 실패를 튀게 하고 · 펼치면 원문(접힘이 기본). 권한 때문에 안 왔으면 그 사실을 적는다: 빈칸은 "없다" 로 읽힌다.
  • 한 일이 위, 도구 로그가 아래다(REQ-WEB-124). 첫 물음은 "무슨 도구를 썼나" 가 아니라 "무엇을 하는 중이고 막혀 있나" 다. 궤적은 새로 저장하는 것이 없다 — 이벤트가 이미 세션 id 를 달고 있다.
  • 버전 목록은 누를 수 있어야 한다(2026-09-01 — 사람 요청 · REQ-WEB-121·122). 서버는 처음부터 이것을 줄 수 있었다 — EP-SPEC-06 이 요구사항 델타와 줄 diff 를 함께 돌려주는데(2026-08-22) 웹이 그 경로를 한 번도 부르지 않았고, 그래서 테스트도 0건이었다. 레일 클릭은 ?diff=vN-1..vN, 옆의 [이 버전 전문]은 ?v=N. 임의의 두 버전은 diff 머리의 select 둘로 고른다 — 순서는 항상 오래된 쪽 → 새 쪽으로 정규화한다(뒤집힌 diff 는 "전부 삭제됨" 으로 읽힌다).
  • 요구사항 델타가 본문 diff 보다 앞에 온다(§4.3). 리뷰에서 묻는 것은 "문구가 어떻게 바뀌었나" 가 아니라 "약속이 늘었나 줄었나 달라졌나" 다. 기본은 변경분만이고, 접은 자리는 빈칸이 아니라 몇 줄인지 적는다.
  • 받은 요청에서 문서로 간다(2026-08-31 — 사람 요청 · REQ-WEB-119·120). 결재하려면 본문을 봐야 하는데 카드에는 제목과 키뿐이었고, 키는 글자였을 뿐이라 그 문서를 보려면 목록에서 손으로 찾아야 했다. 키를 링크로 만들고 카드 안에서 본문을 펼친다 — 펼칠 때 받아 오고, 검토 중인 그 버전을 받는다(카드가 보여준 것과 승인되는 것이 같아야 한다). 질문 카드의 발견은 ?finding= 으로 리뷰 센터의 그 지적을 편다.
  • 처분은 넷이다(2026-08-30 — 사람 요청 · REQ-WEB-117). 구현이 맞고 스펙이 틀린 지적은 코드가 아니라 문서를 고쳐 닫힌다 — 그 길이 없으면 사람도 에이전트도 남은 값 중 아무거나 고르고, dismissed(오탐이 아니었다)나 wont_fix(고쳤다)가 둘 다 거짓 기록이 된다(4.4 REQ-API-060). 증거는 그 스펙의 지금 버전이라 사람에게 버전 id 를 묻지 않는다: 문서만 고르면 화면이 채운다. 고르개는 본문 링크와 같은 것을 쓴다.
  • 피드백이 기록으로 끝났다(2026-08-30 — 사람 물음). 사람이 할 수 있는 것은 처분 3종뿐이라 "왜 그렇게 봤는지"를 적을 자리가 없었고, 무엇을 적든 지적한 에이전트는 듣지 못했다. 레일에 코멘트를 둔다(REQ-WEB-114) — 그 말은 그 발견을 올린 세션의 하트비트로 돌아간다(4.4 REQ-API-058). 그리고 Task 로 올리는 단추(REQ-WEB-115): wont_fix 는 큐에서 지우는 것이지 잇는 것이 아니라, "나중에 하자"가 갈 곳이 없었다.

와이어프레임과 다른 세 곳, 그리고 그 이유.

  1. finding·리뷰 세션에 표시 키를 만들지 않는다. 와이어프레임의 FND-4a19·RVS-5e72는 예시 표기이고, 표시 키 정본(3.3 데이터 모델 §5.1)의 타입 문자는 T(Task)·S(Spec) 둘뿐이며 finding·review_session 테이블에는 key 열 자체가 없다(4.3 §2.7). 타입 문자를 늘리는 것은 새 결정이라 사람 확인 없이 하지 않는다 — 화면은 UUID 뒤 8자를 "짧은 id"로 명시해 보여주고, 사람이 옮겨 적는 식별자는 file:line과 severity다. 뒤쪽인 이유: UUIDv7의 앞 48비트는 생성 시각이라 같은 리뷰에서 나온 발견들이 앞자리를 통째로 공유한다(실측 2026-08-23 — 시드 화면에서 세 발견이 전부 01990a66이었다). 구별되는 것은 난수 쪽뿐이다.
  2. 리뷰가 없는 브랜치의 면제는 이 표에 뜨지 않는다. 면제(approval.is_bypass)는 리뷰 세션을 주체로 붙는데 approval.subject_id는 uuid이고 브랜치는 문자열이라(4.3 §2.8), 세션이 없으면 면제를 그 줄에 실을 길이 없다 — 와이어프레임 §2.6 ⑧의 미커버 + BYPASS 1 줄이 여기 해당한다. 담으려면 결재에 브랜치를 적을 자리가 필요한데 그것은 스키마 결정이라 사람 확인 전까지 하지 않는다.
  3. spec_drift의 CR 라우팅 버튼이 없다. CR 생성(FR-04)이 Phase 2의 다른 조각이라 보낼 곳이 아직 없다. 대신 spec_drift 태그와 유래 스펙 링크를 준다 — 눌러서 아무 일도 안 일어나는 버튼보다 낫다.

3.2 md 직렬화 왕복 규칙

저장 포맷은 markdown이고 메타는 DB 컬럼이다(D-09). 왕복 계약:

  1. 저장 경로: 에디터 문서 → serialize(md) → PUT .../draft(body_markdown). 서버는 content_hash = sha256(body_md)로 무변경 저장을 차단한다(data-model §2.2 spec_version).
  2. 왕복 검증: 저장 전 클라이언트가 serialize(parse(serialize(doc)))와 serialize(doc)의 일치를 확인한다. 불일치(직렬화 비안정)면 저장을 막고 소스 보기 + 오류 리포트를 안내한다 — 이 실측이 Milkdown 재검토 트리거의 입력이다.
  3. 정규화는 serializer가 결정한다: 리스트 마커·표 정렬·공백 정규화 규칙은 단일 serializer 구현에 고정하고, 웹과 터미널이 같은 draft를 오가도 정규화 차이만으로 diff가 생기지 않게 한다.
  4. 파싱 실패 허용: 터미널에서 저장된 md에 화이트리스트 밖 구문이 있으면 에디터는 해당 블록을 원문 보존 read-only 블록으로 렌더링한다. 본문을 임의로 재작성하지 않는다(정보 손실 0 원칙 — importer.md와 동일).

스펙 편집기(TipTap)와 소스 보기가 쓰는 유일한 본문 스타일이다. Tailwind preflight가 h1~h6·ul·ol의 기본 스타일을 전부 지우므로, 이 클래스가 없으면 스펙 문서가 한 덩어리 평문으로 보인다(v0.5 구현에서 실제로 그랬다 — 클래스 이름만 있고 정의가 없었다). 스펙을 읽고 고치는 것이 이 제품의 중심 행위라 여기가 비면 제품이 비는 것과 같다.

점화 기록 — 다크 팔레트 구현 방식

@media (prefers-color-scheme: dark) { @theme { … } } 로 다크 값을 정의했더니 Tailwind v4가 중첩된 @theme을 최상위로 끌어올려 미디어 조건을 지웠다. 결과적으로 다크 값이 라이트 값을 무조건 덮어써서 앱은 언제나 다크였고, 라이트 팔레트는 죽은 코드였다(2026-08-23 실측). 토큰은 이미 :root의 CSS 변수이므로, 다크는 평범한 CSS(@media { :root { --color-…: … } })로 그 변수만 다시 정의한다. 같은 이유로 --shadow-*는 @theme에 두지 않는다 — Tailwind가 빌드 시점에 값을 박아 넣어 다크에서 바뀌지 않는다.

한 줄에 놓이는 필드 — FieldRow (2026-08-29 신설 — 사람 보고)

이름·slug·키를 한 줄에 놓은 폼에서 "이름"만 한 단 아래로 내려앉아 있었다(프로젝트 추가). 원인은 정렬 축이었다: 줄이 items-end 라 상자의 아래 끝만 맞았는데, 힌트가 있는 필드와 없는 필드는 키가 다르므로 힌트 없는 쪽의 라벨과 입력이 통째로 내려간다. 사람의 눈이 따라가는 것은 상자의 밑변이 아니라 입력의 줄이다.

FieldRow 는 세 줄짜리 격자(라벨 / 입력 / 힌트)를 만들고, 각 Field 가 subgrid 로 그 줄을 나눠 쓴다. 힌트가 없는 칸은 비어 있을 뿐 자리는 그대로라, 필드를 더하고 빼도 줄이 흔들리지 않는다.

  • 버튼처럼 필드가 아닌 것은 FieldRowAction 으로 감싸 입력 줄에 놓는다. 그냥 두면 아래 끝(=힌트 줄)에 붙는다.
  • 줄 간격은 부모가 갖는다. subgrid 자식이 자기 gap 을 또 선언하면 그만큼 칸이 어긋난다(실측 2px).
  • justify-start 가 필요하다. 자동 트랙은 남는 가로를 나눠 가지므로 그대로 두면 버튼이 카드 끝까지 늘어난다.
  • 좁은 화면(max-md)에서는 줄로 흐른다 — 그때 FieldRowAction 은 자리를 지정하지 않는다. 2행이 첫 필드의 입력 칸이라, 못 박아 두면 버튼이 폼 맨 위로 올라간다(실측).

실측(1440×900): 라벨 3개가 같은 y(437), 입력 3개와 버튼이 같은 y(458). 고치기 전에는 "이름"의 라벨·입력이 20px 아래였고 버튼은 힌트 줄에 붙어 있었다.
