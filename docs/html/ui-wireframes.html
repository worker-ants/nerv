1. 정보 구조(IA)와 내비게이션

1.1 화면 설계 5원칙

이 문서의 모든 화면 결정은 아래 다섯 원칙에서 파생된다. 원칙 1·2는 문제 정의(P4·P7)에서, 3·4는 협업 플랫폼의 에이전트 통합이 정리한 업계 수렴 패턴에서, 5는 clemvion 하네스 분석이 검증한 운영 경험에서 나왔다.

① 화면은 요구사항의 렌더링이다

모든 화면 요소에 FR/D 번호가 붙는다. 번호가 없는 요소는 그리지 않고, 반대로 FR에 있는 상태는 어느 화면에든 반드시 드러난다. 이 페이지의 legend가 그 대응표다.

② 묻지 않아도 보인다

P4의 본질은 정보 부재가 아니라 합성 비용이었다. clemvion에서 "다음에 뭘 하지"의 답은 로드맵 표 + spec status + in-progress 풀 + 감사 스크립트 2종을 사람이 눈으로 합쳐야 나왔다. NERV의 화면은 서버가 합성을 끝낸 결과만 보여준다.

③ 에이전트는 항상 자신을 밝힌다

사람과 에이전트가 같은 리스트에 섞여도 액터 타입은 배지로 구분된다(D-08). Linear의 "에이전트는 자신이 에이전트임을 항상 밝혀야 한다"와 GitHub 감사 로그의 actor_is_agent를 UI 계약으로 옮긴 것이다.

④ 행동은 카드 위에서 끝난다

승인·거절·코멘트, attach·stop, finding 해소는 목록을 떠나지 않는다. 다만 되돌릴 수 없는 행동(거절·stop·게이트 면제)은 사유 입력을 한 단계 요구한다.

⑤ 모르면 모른다고 말한다

게이트 판정 불가·플랫폼 연결 끊김·하트비트 유실은 조용히 통과시키되 배너로 드러낸다(D-14, NFR-05). 조용한 실패는 화면 설계 차원의 금지 사항이다.

읽는 법

예시 데이터는 3.1 비전과 핵심 시나리오의 페르소나(지민·서연·도현·하나·유나)와 동일한 인물·호스트·수치를 쓴다. 와이어프레임은 레이아웃과 정보 우선순위를 정의할 뿐 최종 비주얼이 아니다.

✅
설계 결정 D-08 · 행위자 모델: 사람 assignee + 에이전트 delegate 분리

화면에서 이 결정은 세 가지로 나타난다. ① Task 카드에 사람 아바타(assignee)와 AI 배지(delegate)가 동시에 찍힌다. ② 활동 피드·감사 로그의 모든 항목에 is_agent 구분이 보인다. ③ 에이전트가 단독으로 소유한 항목은 존재하지 않는다 — 책임자는 언제나 사람이다.

1.3 내비게이션 맵

화면 간 이동은 대부분 "숫자를 클릭하면 그 숫자를 만든 레코드로 간다"는 한 가지 규칙을 따른다. 커버리지 게이지의 28은 Requirement 목록으로, finding 큐의 3은 finding 상세로, 세션 카드의 diff는 PR로 간다.

그림 2. 내비게이션 맵 — 실선은 정방향 이동, 점선은 출처 역추적(S6 → S3)
  • S7 → 요청 세션 딥링크: 질문에 답하면 카드가 "요청 세션 mac-02/claude-code에 전달됨"으로 바뀌고, 그 텍스트가 S5 세션 상세로 가는 링크가 된다.
  • S6 → S3 역추적: 모든 finding은 유래한 SpecVersion·Requirement를 갖는다(FR-09·FR-13). 이것이 P5(리뷰 출처 추적 곤란)의 화면 상 해답이다.
  • S5 → git forge: diff 통계와 브랜치명은 PR로 나가는 외부 링크다. NERV는 코드 호스팅을 대체하지 않는다.

1.4 URL 규약

규칙형태이유
리소스는 항상 안정 ID로 지목/p/clemvion/specs/SPC-CWC-007경로·제목이 바뀌어도 링크가 깨지지 않는다(FR-01, D-09). clemvion의 인덱스 문서 부패는 경로 참조가 원인이었다
프로젝트 스코프는 URL 두 번째 세그먼트/p/{project}/…권한 검사 지점이 라우팅과 일치한다(FR-14)
뷰 상태는 쿼리로?diff=v3..v4, ?severity=critical공유 가능한 링크. 승인 요청 알림에 그대로 붙는다
세션·작업은 전역 유일 ID/p/clemvion/sessions/S-8f31훅·MCP 응답이 반환하는 딥링크와 동일 형태(FR-07·FR-15)
ℹ️
예시 ID 표기에 대하여

표기용 예시 ID(SPC-/REQ-/TSK-/S-/FND-/CR- 접두)는 이 문서의 화면 예시를 읽기 쉽게 하기 위한 것이다. 실제 ID 발급 규칙(서버 발급 해시 기반, D-04)과 접두 확정은 3.3 데이터 모델이 정의한다.

3.1 색은 "사람이 지금 무엇을 해야 하는가"로 배정한다

상태 값은 엔티티마다 다르지만 색은 여덟 가지뿐이다. 엔티티별로 색을 따로 정하면 화면을 넘나들 때 학습이 리셋된다. NERV는 색을 행동 축에 배정하고 모든 엔티티가 그 축을 공유한다.

4. 인터랙션 노트

4.1 승인 카드 — 원클릭 승인 / 거절 / 코멘트

  • 승인: 즉시 반영, 카드가 접히고 "처리됨" 트레일에 3분간 남는다. 되돌리기 링크 제공.
  • 거절: 사유 입력이 필수다. 사유는 요청자 알림과 감사 로그 양쪽에 들어간다(FR-16).
  • 코멘트: 상태를 바꾸지 않고 스레드에 남긴다. 질문 카드에서는 선택지 + 코멘트를 함께 보낼 수 있다.
  • 지시자≠승인자: 요청자와 승인자가 같으면 승인 버튼이 비활성화되고 툴팁으로 사유가 뜬다. 에이전트가 제안한 CR은 위임한 사람도 단독 승인할 수 없다.
  • 일괄 처리: 같은 유형 · 같은 스펙의 저위험 항목만 일괄 승인 가능. 위험도 게이트(D-06)가 저위험으로 분류한 것에 한한다.
  • 전달 확인: 처리 즉시 카드에 "요청 세션 linux-ci-01/codex에 전달됨"이 표시되고, 세션 상태가 awaiting_input → active로 바뀌는 것이 S5에 반영된다.

4.2 세션 카드 — attach · steer · stop

  • attach ↗: 세션 상세(Activity 타임라인)로 가는 딥링크이자, 로컬 세션이라면 nerv://session/S-8f31 형태의 핸드오프 링크다. 터미널 UI들이 Enter로 세션에 붙는 조작을 웹에서 재현한 것.
  • steer: 세션을 멈추지 않고 지시를 큐잉한다. 다음 하트비트/폴링 시점에 에이전트가 수령한다. 스티어링을 1급 동작으로 둔 것은 GitHub mission control과 Linear의 후속 지시 패턴에서 검증된 설계다.
  • stop: 확인 다이얼로그 + 사유. 이미 푸시된 커밋은 보존되고, 클레임은 즉시 회수되어 Task가 ready로 돌아간다.
  • 자동 갱신: SSE로 5초 이내 반영(NFR-02). 연결이 끊기면 배너 + 폴백 폴링.
  • 스티어 메시지는 승인이 아니다: 다른 세션 · 에이전트가 보낸 메시지는 사람의 승인으로 취급되지 않는다. Claude Code agent teams가 메일박스 설계에서 세운 보안 불변식을 그대로 채택한다(NFR-03).

4.3 스펙 diff 뷰 — 버전 diff와 CR 델타

종류진입표기
버전 diffS3의 diff v3..v4 토글줄 단위 +/−, 변경 문단 좌측 세로 막대, 헤딩 단위 접기
CR 델타S7 CR 카드 → 델타 전체 보기절 단위 ADDED / MODIFIED / REMOVED 카운트 + 변경 절만 렌더링
  • 기본 뷰는 변경분만이다. 전체 문서 보기는 토글로 둔다. 리뷰어가 1,750줄을 처음부터 읽게 만드는 순간 승인은 형식이 된다.
  • 코멘트는 diff 뷰에서도 헤딩 앵커에 붙는다. 줄 번호에 붙이면 다음 버전에서 고아가 된다.
  • CR 승인 시 영향받는 Task가 재계산되고, 그 목록이 승인 직전 확인 단계에 표시된다(FR-04 · FR-05).

4.4 커버리지 드릴다운

그림 3. 커버리지 드릴다운 — 게이지 → 영역 → Requirement → 증적 → 행동

드릴다운의 끝은 항상 행동이다. "증적 없음"에서 멈추지 않고 그 자리에서 검증 Task를 만들 수 있어야 커버리지 숫자가 관리 대상이 된다(FR-13). 이 경로는 QA 페르소나(하나)의 하루에서 가장 많이 쓰인다.

4.5 실시간성 · 알림

  • SSE로 세션 보드 · 승인함 배지 · 커버리지 숫자를 갱신한다. 목표는 5초 이내(NFR-02).
  • 채널 라우팅: 승인 요청 · 질문은 즉시(인앱 + Slack), 상태 변화는 다이제스트. 기본값이 다이제스트인 이유는 알림 피로가 승인 품질을 떨어뜨리기 때문이다(FR-12).
  • 알림에서 화면으로: 모든 알림은 처리 가능한 화면의 딥링크를 포함한다. "무슨 일이 있었다"만 알리고 끝나는 알림은 만들지 않는다.

4.6 접근성 · 반응형 · 키보드

  • 상태는 색 + 텍스트 + 아이콘 3중 인코딩. 색만으로 구분되는 정보는 없다.
  • 세션 보드 · 작업 보드는 좁은 화면에서 카드 스택으로 접힌다. hostname · 하트비트 · diff는 축약해도 삭제하지 않는다.
  • 승인함은 키보드만으로 처리 가능해야 한다(j/k 이동, a 승인, r 거절, c 코멘트). 하루 수십 건을 처리하는 화면이라는 전제.
  • 모든 표는 가로 스크롤 컨테이너 안에 있고, 본문이 가로로 밀리지 않는다.
